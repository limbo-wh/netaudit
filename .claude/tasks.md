## Температуры видеокарты: показывался самый холодный датчик (2026-09-14)

Пришло из разговора о ПК: у прежнего владельца машины в PUBG был чёрный экран
с вентиляторами видеокарты на максимум. Симптом характерен для перегрева памяти
карты — а приложение эту температуру не показывало вовсе.

- [x] `TemperatureProbe.BestTemperature` возвращал датчик по первому совпадению
      с «GPU Core» и до горячей точки с памятью не доходил никогда. Комментарий
      при этом утверждал обратное — «у многодатчиковых GPU это горячее ядро».
      Разделено: у процессора берётся сводный датчик, у видеокарты — максимум
- [x] Проверено на живой RTX 2080 SUPER: ядро 57 °C, горячая точка 68 °C,
      память 67 °C. Приложение показывало 57
- [x] Добавлен `SampleGpu()` — раздельные ядро / горячая точка / память плюс
      разрыв между горячей точкой и ядром
- [x] В диагностику видеокарты добавлен блок температур: в покое и повторно
      после нагрузки, с разбором разрыва (>25 °C под нагрузкой — высохшая
      термопаста) и порогом для памяти (95 °C)
- [x] Окно нагрузки следило за температурой из `nvidia-smi`, то есть за ядром:
      аварийный порог 97 °C не сработал бы при перегретой памяти. Теперь берётся
      максимум из обоих источников
- [x] Ноль от заблокированного драйвера протекал как настоящее показание: датчик
      «Core (Tctl/Tdie)» остаётся в списке со значением 0,0, а проверка смотрела
      только на `null`. Процессор показывался с температурой 0 °C вместо
      «неизвестно» — тот же класс ошибок, что чистили в аудите переносимости
- [x] Доступность датчиков разделена на процессор и видеокарту: процессору нужен
      драйвер ядра, видеокарта NVIDIA читается через NVAPI. Раньше без прав
      администратора проба выходила сразу и температуры карты не было вовсе,
      хотя она доступна обычному пользователю — проверено
- [x] **Карта была зажата режимом питания драйвера — теперь приложение это
      видит.** 14.09: RTX 2080 SUPER под любой нагрузкой (своей, FurMark, окно,
      весь экран) держала 1200 МГц из 2130 при 180 Вт из 250, без троттлинга,
      с маской причин «Idle». Три часа ушло на блок питания (12 В под нагрузкой
      11,6–11,8 — в норме), композитор Windows, лок частот (`nvidia-smi -rgc`
      с правами — «All done», без изменений) и собственный шейдер. Причина —
      «Оптимальное энергопотребление» в панели NVIDIA, умолчание драйвера. После
      переключения: 1650 МГц, 243 Вт, маска «Pwr», FurMark 159 FPS вместо 90.
      Сделано: `NvidiaLiveProbe` читает `clocks_event_reasons.active`; в
      диагностике видеокарты новый блок «Поведение под нагрузкой» — частота от
      предела, мощность от лимита, причина; вердикт «зажата режимом питания» с
      инструкцией. Пороги: частота < 75% предела и мощность < 85% лимита
- [x] **Оверлей: загрузка видеокарты от самой карты.** `SystemMetricsScheduler`
      поднимает `NvidiaLiveProbe` и берёт загрузку из неё, счётчик Windows
      остаётся для карт без nvidia-smi. Без прав администратора оттуда же
      берётся температура ядра — раньше была бы прочерком
- [x] **Оверлей: температура видеокарты как «ядро/гор. точка»** с подписью
      «GPU ядро/гор.»; цвет по горячей точке (85 / 95). Когда горячей точки
      нет — одна цифра и прежняя подпись. В снимке метрик два новых поля:
      `GpuCoreTempC`, `GpuHotSpotC`
- [x] Оверлей после правок проверен вживую по скриншоту Release-сборки:
      «GPU ядро/гор. 46/57°C», «Темп. CPU —», приложение без сбоев
- [ ] `[?]` **Температура памяти: FurMark 90 °C, LibreHardwareMonitor 84 °C** в один
      и тот же момент под FurMark. Разные пути чтения; GPU-Z для Turing память
      не показывает вовсе, `nvidia-smi` тоже (`N/A`), собственный лог FurMark
      с этим полем не создался. Третьего источника на машине нет — сверить
      можно только владельцу, поставив HWiNFO рядом с нашим оверлеем под
      нагрузкой. До тех пор в отчётах — цифра LibreHardwareMonitor с оговоркой
- [x] **Оверлей: «Кадры 4» под FurMark** — счётчик честный: кадры окна в фокусе
      (браузер), FurMark на OpenGL через события DXGI не проходит. В README
      добавлено пояснение; в оверлее места под подпись нет
- [x] Блок «Поведение под нагрузкой» проверен на живой сцене после прогона:
      1650 МГц (77% предела), 195 Вт (78% лимита), маска пустая → «работает
      в полную силу». Та же сцена дала 91 к/с против 57–82 вчера
- [x] **Стресс-тест видеокарты усилен до потолка вычислительной нагрузки.**
      Было 135 Вт при 1650 МГц; стало 188–192 Вт (77% лимита) при 1920–1935 МГц,
      горячая точка 74, память 73. Добавлен поточный шейдер — линейное чтение
      буфера отдельным вызовом между счётными, по одному float4 на поток,
      объём второй осью вызова. Три тупика по дороге: копирование внутри одного
      буфера шло на 12 ГБ/с (чтение и запись одного ресурса сериализуются);
      восемь чтений на поток с шагом 256 МБ — 95 ГБ/с (таблица страниц карты);
      калибровка мерила первый вызов с компиляцией шейдера и обрывалась на
      минимуме — добавлен прогрев. Мощность одинакова при любом балансе счёта и
      памяти — это предел compute на этой карте: FurMark берёт 250 Вт
      растеризацией и текстурами, которых у вычислительного шейдера нет
- [x] **Окно «Железо» предупреждает о гигабитном контроллере на 100 Мбит** —
      кабель или порт роутера; гигабитность узнаётся по имени (GbE, Gigabit,
      1000, 2.5G, Intel I2xx), нераспознанное — молчим. Проверено на живых
      данных: срабатывает на Realtek GbE / 100 Mbps
- [x] **Паспорт железа перечислял 28 «адаптеров»**: фильтры WFP и QoS по три на
      карту, десять WAN Miniport, Teredo, 6to4, IP-HTTPS, отладчик ядра.
      Псевдоадаптеры отфильтрованы, VPN-туннели с адресом остаются
- [x] **Сбой PUBG воспроизведён (14.09 15:40:53).** FurMark 6 ГБ + стресс
      процессора 100% и память 4 ГБ: через 28 с после выхода карты на мощность
      она зависла намертво — ядро 63, горячая точка 72, память 70, 12 В на
      разъёмах 11,5/11,7/11,8, напряжение ядра до 1,05 В, мощность прыгала
      140→261→139 Вт. Процессор и память работали ещё минуту, кнопка питания
      в 15:41:39, Kernel-Power 41 с кодом 0, дампов и записей драйвера нет.
      Соло FurMark 32 мин и память 1,66 ТБ — чисто. Диагноз: питание под
      совместной нагрузкой. Дальше — решение владельца: блок питания
      глазами; эксперименты с `-pl 200` и лимитом буста — с риском повтора
- [x] Инструмент отработал как задуман: три источника (GPU-Z, наблюдение,
      чёрный ящик) дали хронологию до секунды; чёрный ящик писал строки хода
      стресс-теста до последней секунды перед кнопкой
- [ ] Отчёт о сбоях: событие 41 с `PowerButtonTimestamp` ≠ 0 показывается как
      «выключено кнопкой питания» — верно, но в этом случае кнопку нажали
      после зависания карты. Стоит рядом показывать, была ли карта жива

## Аудит слоя интерфейса: 16 дефектов (2026-09-14)

      собственное закрытие, а не через планировщик; в отчёте формулировка
      «сеанс оборван» остаётся честной
- [ ] Чтение SMART: `Get-StorageReliabilityCounter` на этих SATA SSD отдаёт
      пусто, часы наработки и износ не видны (старый долг, теперь подтверждён
      на живых дисках)

## Переносимость тестов на чужие сборки (2026-09-14)

Владелец спросил, как тесты поведут себя на других машинах. Разбор выявил два
места, где на слабом железе было бы плохо, — оба исправлены.

- [x] **Игровой замер мог уронить видеодрайвер на слабой карте.** Сложность
      шейдера была зашита константой под RTX 2080 SUPER (кадр 10 мс). На
      встроенной графике, которая в десятки раз медленнее, тот же кадр считался
      бы сотни миллисекунд, а на совсем старой — перевалил бы за две секунды,
      после которых Windows перезапускает драйвер. Добавлена калибровка: замер
      одного настоящего кадра и упрощение сцены, если он дольше 250 мс. На
      быстрой карте сложность остаётся стандартной, иначе результаты разных
      машин стало бы не сравнить; упрощение отмечается в отчёте
- [x] **Замеры скорости требовали 512 МБ видеопамяти** двумя буферами по 256 МБ.
      У встроенной графики память общая с системной, и выделение могло не
      пройти — тест падал бы с ошибкой вместо того, чтобы померить на меньшем
      объёме. Теперь размер снижается по цепочке 256 → 128 → 64 → 32 → 16 МБ,
      уменьшение отмечается в выводе
- [x] Проверено, что правки ничего не сломали на этой машине: игровой замер
      95 кадров, скорости памяти и FP32 прежние
- [ ] **Паспорт видеокарты у AMD и Intel будет неполным.** VBIOS, состояние шины

      вендоров этих полей не будет. Всё остальное (DXGI, Direct3D) универсально.

- [ ] Тензорные блоки через DirectML работают у всех вендоров, но на картах без

## Строка FPS в оверлее (2026-08-17)

- [x] **Найден и исправлен настоящий баг, из-за которого счётчик всегда показывал
      прочерк.** `_session.Source.AllEvents` отдаёт «сырые» события без разбора
      манифеста — `TaskName` для DXGI/D3D9 приходил как `"EventID(42)"`, а не

      никакой ошибки не было — просто событий с нужным именем не приходило

      имена через TDH правильно
- [x] Заодно исправлена вторая, более тонкая ошибка: фильтр был `Contains("Present")`,
      а у DXGI три разных семейства событий с «Present» в имени — `Present`,
      `IDXGISwapChain_Present`, `PresentMultiplaneOverlay`. При рабочем
      резолвинге имён это утроило бы счётчик. Заменено на точное `== "Present"`
- [x] **Проверено на живой Dota 2, права администратора получены через elevation
      на этой же машине.** Отдельный диагностический консольный инструмент

      = 52,6 FPS у dota2.exe — правдоподобное число, не через край и не ноль.

      корректность подсчёта
- [x] Добавлена самодиагностика: `FpsProbe.EventsSeen`/`PresentsMatched`
