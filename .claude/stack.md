# Стек NetAudit

Обновлять этот файл при любом изменении технологий, версий или ключевых решений.

## Платформа

| Что | Выбор | Почему |
|---|---|---|
| ОС | Windows 10/11 x64 | ETW, WlanAPI, оверлей — всё Windows-only |
| Runtime | .NET 10 (LTS) | .NET 8 уходит с поддержки в ноябре 2026 |
| SDK на машине | 10.0.400 (`C:\Program Files\dotnet\sdk`) | проверено |
| TargetFramework | `net10.0-windows` во всех проектах | в Core есть Win32 P/Invoke |
| UI | WPF (`UseWPF=true`) | layered-окна, P/Invoke, зрелость |
| Язык | C# 13, `Nullable=enable`, `ImplicitUsings=enable`, `AllowUnsafeBlocks=true` | |

## Пакеты

| Пакет | Проект | Роль |
|---|---|---|
| `ScottPlot.WPF` 5.* | App | realtime-графики через `DataStreamer` |
| `System.Management` 10.0.11 | Core | WMI — железо, GPU, ОС |
| `System.Diagnostics.PerformanceCounter` 9.0.5 | Core | CPU/RAM/GPU счётчики |
| `Microsoft.Diagnostics.Tracing.TraceEvent` 3.2.5 | Core | ETW: счётчик FPS готов, сетевой трафик по процессам (этап 3–4) — ещё нет |
| `Microsoft.Data.Sqlite` | Core — **ещё не добавлен** | история сессий (этап 6) |

`UseWindowsForms=true` в `NetAudit.App.csproj` — ради `NotifyIcon` (значок в трее).
Своего значка трея у WPF нет, а WinForms уже входит в тот же Windows Desktop
Runtime, что и WPF — лишнего веса это не добавляет. Побочный эффект: `Brush`,
`Application`, `Color`, `Size` существуют в обоих UI-фреймворках и конфликтуют
через неявные `using`. Лечится в csproj:
```xml
<Using Remove="System.Drawing" />
<Using Remove="System.Windows.Forms" />
```
WinForms явно подключается только в `TrayIcon.cs`, через `using Forms = System.Windows.Forms;`.

## Ключевые технические решения

**Оверлей — layered-окно, не хук.** `WindowStyle=None` + `AllowsTransparency=true` +
P/Invoke `SetWindowLong(GWL_EXSTYLE, WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE)`.
Инъекция DLL / хук DXGI **запрещены** — EAC, BattlEye, Vanguard, FACEIT дают за это бан.
Для exclusive fullscreen — только RTSS shared memory (он в белых списках античитов).

Borderless-игра перехватывает Z-order → `DispatcherTimer` раз в 1.5 с зовёт
`SetWindowPos(HWND_TOPMOST, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE)`.
`SWP_NOACTIVATE` обязателен, иначе игра вылетает из фокуса каждый тик.

**Управление оверлеем — только хоткеи.** Окно сквозное по построению, мышью его
не подвинуть и не нажать. `RegisterHotKey` на HWND главного окна + `WM_HOTKEY`
через `HwndSource.AddHook`. Флаг `MOD_NOREPEAT` обязателен — без него зажатая
клавиша шлёт поток событий. Комбинации: Ctrl+Alt+O — вкл/выкл, Ctrl+Alt+1…4 — углы.
Занятую другим процессом комбинацию `RegisterHotKey` просто не даёт — это штатно,
пишем предупреждение в лог и работаем дальше.

**Настройки применяются мгновенно.** Каждый контрол `SettingsWindow` подписан на
изменение → `SaveToSettings` + `Save()` + `_onApply()`. Кнопки «Применить» нет.
Два обязательных условия, без которых это ломается:
- флаг `_loading` на время первичной расстановки контролов — иначе события
  расстановки затирают настройки полусобранными значениями;
- снимок `AppSettings.Clone()` при открытии окна; «Вернуть как было» зовёт
  `CopyFrom(snapshot)`. Именно `CopyFrom`, а не подмена ссылки: экземпляр
  `AppSettings` уже роздан главному окну и оверлею.

**Разметка оверлея — `Grid.IsSharedSizeScope` + `SharedSizeGroup`.** Колонка подписей
общая для всех строк; жёсткая ширина ломалась при смене размера шрифта и на длинных
подписях вроде «Потери шлюз».

**ICMP не требует админа.** `System.Net.NetworkInformation.Ping` — обёртка над
`IcmpSendEcho2`, не над raw-сокетами. Traceroute через `PingOptions.Ttl` — тоже без админа.

**UDP remote-адрес — только через ETW.** `GetExtendedUdpTable` remote-адрес не отдаёт,
это тупик. Провайдер `Microsoft-Windows-Kernel-Network`, события `UdpIpSend`/`UdpIpRecv`.
Требует прав администратора → манифест поднимается до `requireAdministrator` только
на этапе 3, не раньше.

**Тайминги.** `PeriodicTimer` + `Stopwatch`. `System.Timers.Timer` неточен и не годится.
Штатное разрешение таймера Windows 15.6 мс — для тика 250 мс достаточно,
`timeBeginPeriod` не трогаем.

**Графики.** Только `DataStreamer`/`DataLogger` из ScottPlot 5 — они рассчитаны на
скользящее окно. Пересоздание `Scatter` на каждом тике — главная причина тормозов
самодельных realtime-графиков, так не делать.

Три вещи про `DataStreamer` 5.1.59, каждая стоила отладки:

- **Значение под курсором он не отдаёт.** Держим своё зеркало данных
  (`Ring` в `MainWindow`) и читаем из него.
- **Координата X — это номер слота в буфере (0…Capacity)**, а точки прижаты
  к правому краю. Индекс считается как `round(xData) − (Capacity − Count)`.
  Считать через долю оси нельзя: при неполном буфере и при зуме промахивается.
- **`ManageAxisLimits` переустанавливает пределы осей на каждой отрисовке.**
  На время зума его надо выключать, иначе ось возвращается на место мгновенно
  и увеличение выглядит несработавшим. Пропустить только свой `AutoScale()` мало.

**Зум графиков — свой.** `UserInputProcessor.Disable()`, выделение рисуем WPF-овским
`Rectangle`, пределы ставим через `Axes.SetLimits`, сброс — двойным кликом.
После любой смены осей курсорный слой надо прятать явно: он не пересчитывается,
пока мышь не двинется, и остаётся висеть с неверным значением.

**Буферы.** В памяти: пинг 2400 точек (10 мин × 4 Гц), системные метрики 300 (5 мин × 1 Гц).
Полная история — в SQLite (этап 6).

## Сборка и поставка

```powershell
dotnet build "C:\Users\Admin\project claude\app_lan\NetAudit\NetAudit.slnx"
.\publish.ps1          # publish + подпись + zip в dist\
.\sign-setup.ps1       # разово: создать самоподписанный сертификат
```

Поставка: `dist\NetAudit-vX.Y.Z-win-x64.zip`, framework-dependent, `PublishReadyToRun=true`.
Внутри — `install.bat` (ставит .NET Runtime, доверяет сертификату, кладёт ярлык).
Настройки живут в `%LOCALAPPDATA%\NetAudit\settings.json`, при обновлении сохраняются.
Версия объявляется в трёх местах и они должны совпадать: `NetAudit.App.csproj`,
`publish.ps1` (`$version`), `version.json`.

## Потребление ресурсов (замерено 2026-08-17)

Итог: **≈6,5% одного ядра** в установившемся режиме со всеми включёнными
функциями, ~163 МБ рабочего набора. До оптимизации было 16–20%.
Первые 10–15 секунд после запуска расход выше (JIT, опрос железа, засев
счётчиков) — мерить надо после прогрева, иначе получите 12% и обманетесь.

Что и сколько стоило, по изолированным замерам:

| Источник | Было | Стало | Как починено |
|---|---|---|---|
| `GpuProbe` | 110–120 мс/тик = **12% ядра** | 1,7 мс = 0,2% | один `ReadCategory()` вместо 108 счётчиков |
| Отрисовка 5 графиков | **+12,1%** | в пределах шума | цикл перерисовки 20 Гц → 2 Гц |
| Лог, все строки | **+10,0%** | +3,4% | строки копятся и отдаются в UI пачками |
| `WifiProbe` (netsh) | 131 мс/5 с = **2,6%** | 0 на кабеле | проверка наличия Wi-Fi адаптера до запуска процесса |
| Опрос процессов | 12 мс/2 с = 0,6% | 0, если вкладка закрыта | пропуск, когда диспетчер не открыт |

**Ключевые уроки, чтобы не наступить снова:**

- Категория «GPU Engine» содержит экземпляр на процесс и движок — на этой машине
  408 штук, из них 108 с `engtype_3D`. Отдельный `PerformanceCounter` на каждый
  и `NextValue()` в цикле — это сотня миллисекунд на тик. Правильно —
  `PerformanceCounterCategory.ReadCategory()` один раз и свои дельты через
  `CounterSampleCalculator`.
- **`ReadCategory()` отдаёт имена экземпляров в нижнем регистре**, в отличие от
  `GetInstanceNames()`. Сравнение обязано быть регистронезависимым, иначе
  не совпадёт ничего и GPU будет молча показывать 0%.
- `ScrollIntoView` на каждой строке лога заставляет список пересчитывать
  разметку. При восьми строках в секунду это дороже всех сетевых проб вместе.
- Запуск `netsh` — это создание процесса, 130 мс. Проверить наличие
  беспроводного адаптера через `NetworkInterface` стоит доли миллисекунды.

Мерить так: отсечь первые 15 секунд, брать `TotalProcessorTime` за 20–30 секунд,
повторить трижды и взять медиану. Машина под фоновой нагрузкой даёт разброс ±3%.

## Тема оформления

Единая тёмно-зелёная тема — `NetAudit.App/Theme.xaml`, подключается через
`App.xaml`. Палитра объявлена там же (`ClrBase`, `Accent`, `Good`, `Warn`, `Bad` и т.д.),
хардкодить цвета в окнах не нужно.

**Почему шаблоны, а не Setter'ы.** Стандартные шаблоны WPF рисуют выпадающий
список `ComboBox`, вкладки `TabItem`, поля ввода, флажки и подсказки светлой
системной темой. Задать им `Background` бесполезно: белый фон приходит из
шаблона, а у `ComboBox` он вообще в отдельном `Popup`. Поэтому в теме именно
`ControlTemplate`.

Три грабли, каждая проверена на живом приложении:

- **`Stroke` требует Brush, а не Color.** `Stroke="{StaticResource ClrBase}"`
  роняет приложение при разворачивании шаблона (`XamlParseException`), причём
  не при старте, а в момент первой отрисовки контрола. Использовать `BgBase`.
- **`ContentPresenter` в шаблоне `TabControl` обязан называться
  `PART_SelectedContentHost`.** Без имени вкладка рисуется правильно, но
  содержимое выпадает из дерева автоматизации: UIA перестаёт видеть все
  контролы внутри вкладок.
- **Локальные `Window.Resources` с неявными стилями перекрывают тему.** Стиль
  `<Style TargetType="Button">` без `Template` в окне возвращает системный
  шаблон и светлый вид. В окнах локальные стили не держим.

Серии графиков: шлюз `#4FD98B`, интернет `#86D97A`, приём `#5CD1C0`,
отдача `#86D97A`, CPU `#E3B44F`, RAM `#D4E8A8`.

## Smart App Control и подпись (важно, проверено 2026-08-17)

На этой машине **Smart App Control включён** —
`HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy` → `VerifiedAndReputablePolicyState = 1`.
Он и есть источник сообщений «приложение частично заблокировано».
Блокировки видны в журнале `Microsoft-Windows-CodeIntegrity/Operational`,
события **3077 / 3033 / 3118**.

Измерено запусками, не по документации:

| Что | Запусков успешно | Блокировок SAC |
|---|---|---|
| dll и exe без подписи | 4 из 4 | 0 |
| dll и exe с самоподписанным сертификатом | 0 из 3 | каждый запуск |
| exe самоподписан, dll без подписи (как делает `publish.ps1`) | 3 из 3 | 0 |

**Правило: не подписывать `NetAudit.App.dll` самоподписанным сертификатом.**
SAC признаёт только сертификаты из своего списка и облачную репутацию; локальное
доверие к сертификату (Root, TrustedPublisher) он **не учитывает**. Неподписанную
управляемую dll он пропускает по репутации, а подписанную недоверенным издателем —
отвергает. То есть самоподписанная подпись dll делает строго хуже, чем её отсутствие.

`publish.ps1` подписывает только exe — это корректно, менять нельзя.
Автоподпись обычных сборок в csproj пробовали и откатили, комментарий с причиной
оставлен прямо в `NetAudit.App.csproj`.

Полностью снять предупреждения могут только два пути, оба вне кода:
отключить Smart App Control (**необратимо**: обратно включается лишь переустановкой
Windows) либо купить коммерческий сертификат подписи. Это решение владельца.

## Счётчик FPS через ETW (2026-08-17)

Кадры считаются по событиям Present провайдеров `DXGI` (`CA11C036-0102-4A2D-A6AD-F03CFED5D3C9`)
и `D3D9` (`783ACA0A-790E-4D7F-8451-AA850511C6B9`) — тот же способ, что у PresentMon
от Microsoft. **Никаких хуков и внедрения в процесс игры** — сеанс ETW читает то,
что Windows и так публикует сама.

Цена: `TraceEventSession` может создать только администратор — это ограничение
самого ETW, не наше. Поднимать всё приложение до `requireAdministrator` ради
одной строки в оверлее неправильно (правило 4), поэтому:
- без прав `FpsProbe.Start()` тихо не срабатывает, `Available = false`, строка
  в оверлее показывает прочерк;
- кнопка «Счётчик FPS: состояние» во вкладке тестов объясняет причину и
  предлагает перезапуск через `Verb = "runas"`, если пользователь захочет.

`Source.Process()` блокирующий — крутится в своём `Thread`, не в `Task`.
`StopOnDispose = true` на сеансе обязателен: без него сеанс ETW переживает
процесс и виснет в системе до перезагрузки.

Охват — Direct3D 9/10/11/12. Игры на Vulkan/OpenGL мимо DXGI не увидены.
**Не проверено эмпирически** — на этой машине нет прав администратора для
запуска сеанса, счётчик ни разу не видел настоящих кадров.

## Игровой режим и распознавание полноэкранных окон (2026-08-17)

`GameModeDetector.Detect()`: сначала `SHQueryUserNotificationState` (ловит
эксклюзивный Direct3D), затем geometry-проверка окна переднего плана против
`MonitorFromWindow`/`GetMonitorInfoW` (ловит borderless).

**Геометрии одной недостаточно.** Развёрнутое обычное окно занимает монитор
не хуже игры — замерено: проводник и Chromium в развёрнутом виде дают
1936×1096 при мониторе 1920×1080, с запасом перекрывая его. Если панель задач
скрывается автоматически, рабочая область совпадает с монитором и отличить
их геометрией уже нельзя. Без дополнительной проверки NetAudit уходил в
игровой режим от развёрнутого браузера и не возвращался.

Признак настоящей игры — отсутствие `WS_CAPTION` в стиле окна (`GetWindowLong(GWL_STYLE)`).
У браузера, проводника, терминала заголовок в стиле окна есть всегда, даже
когда сам заголовок нарисован приложением поверх системной рамки. У игры
в полноэкранном режиме (exclusive и borderless) заголовка нет — она рисует
кадр во весь экран сама. Дополнительно отсекаются известные процессы оболочки
(`explorer`, `TextInputHost`, `ShellExperienceHost` и т.д.) — у них тоже
бывают безрамочные окна во весь экран.

Переключение режима — только после двух одинаковых наблюдений подряд
(`FlipThreshold = 2`, тик раз в 2 с). Без этого alt-tab между игрой и
чем угодно ещё дёргал бы приоритет процесса каждые две секунды.

Что урезается в игровом режиме и что нет — см. `MainWindow.GameMode.cs`.
Частота пинга **не трогается никогда**: это единственное, ради чего
приложение вообще работает во время игры.

## Обновление и установка (2026-08-17)

Автообновление не может переписать собственный exe, пока процесс работает.
Поэтому `UpdateInstaller.DownloadAsync` только скачивает и распаковывает во
временную папку, а подмену файлов делает отдельный PowerShell-скрипт
(`ApplyAndRestart`), который:
1. ждёт завершения процесса по PID (до 30 с);
2. делает резервную копию текущей папки установки;
3. копирует новые файлы; при сбое копирования восстанавливает из резервной копии;
4. запускает обновлённый exe.

**Контрольная сумма обязательна для доверия.** Ссылка на архив приходит из
`version.json` по обычному HTTP(S) без дополнительной защиты — если её не
проверять, подменённый на пути архив выполнился бы от имени пользователя без
единого предупреждения. `release.ps1` считает SHA-256 и кладёт в `version.json`
автоматически; без него `UpdateInstaller` не отказывает намертво, но явно
предупреждает и показывает посчитанную сумму, чтобы решение осталось за
пользователем.

**Не проверено эмпирически** — ни одного релиза ещё не выложено, скачивание
и подмена файлов ни разу не проходили на настоящем архиве.

## Git и релизы (2026-08-17)

Репозиторий: `app_lan/` целиком, ветка `main`. `.gitignore` режет `bin/`, `obj/`,
`dist/`, сертификаты (`*.pfx`, `*.snk`, `NetAudit-cert.cer`) и
`**/.claude/settings.local.json` — с двумя звёздочками, потому что такой файл
есть и в `app_lan/.claude/`, и в `NetAudit/.claude/`, а путь с одной чертой
привязывается только к папке самого `.gitignore`.

`.gitattributes` держит LF в репозитории и CRLF на диске для `.ps1`/`.bat`/`.cmd` —
PowerShell 5.1 читает скрипт с диска, а не через git, и на «чужом» переводе
строки (в связке с отсутствием BOM) уже один раз калечил кириллицу.

`release.ps1` — новый скрипт для выкладки, `publish.ps1` остаётся для быстрой
локальной сборки без счётчика SHA-256. Различие принципиальное: `release.ps1`
обязан обновить `version.json` контрольной суммой, иначе `UpdateInstaller`
не сможет доверять скачанному архиву.

## Границы — не проверено эмпирически

- Поведение layered-оверлея поверх конкретных игр с античитами.
- Структура RTSS shared memory текущей версии (сверять с её SDK-папкой, не гадать).
- Потери ETW-событий под высоким pps.
- Wi-Fi API на Windows 11 24H2+: SSID/BSSID пустые без служб геолокации.
- IPv6-сценарии.
- Счётчик FPS на настоящих кадрах — нет машины с правами администратора для проверки.
- Полный цикл автообновления — нет ни одного выложенного релиза.
- Игровой режим на настоящем эксклюзивном fullscreen (проверено только на
  безрамочном имитаторе и на развёрнутых обычных окнах).
