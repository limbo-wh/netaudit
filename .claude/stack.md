# Стек NetAudit

Обновлять этот файл при любом изменении технологий, версий или ключевых решений.

## Платформа

| Что | Выбор | Почему |
|---|---|---|
| ОС | Windows 10/11 x64 | ETW, WlanAPI, оверлей — всё Windows-only |
| Runtime | .NET 10 (LTS) | .NET 8 уходит с поддержки в ноябре 2026 |
| SDK на машине | 10.0.400 (`C:\Program Files\dotnet\sdk`) | проверено |
| TargetFramework | `net10.0-windows` во всех проектах | в Core есть Win32 P/Invoke |
| UI | WPF (`UseWPF=true`) | layered-окна, P/Invoke, зрелость |
| Язык | C# 13, `Nullable=enable`, `ImplicitUsings=enable`, `AllowUnsafeBlocks=true` | |

`UseWindowsForms=true` в `NetAudit.App.csproj` — ради `NotifyIcon` (значок в трее).
Своего значка трея у WPF нет, а WinForms уже входит в тот же Windows Desktop
Runtime, что и WPF — лишнего веса это не добавляет. Побочный эффект: `Brush`,
`Application`, `Color`, `Size` существуют в обоих UI-фреймворках и конфликтуют
через неявные `using`. Лечится в csproj:
```xml
<Using Remove="System.Drawing" />
<Using Remove="System.Windows.Forms" />
```
WinForms явно подключается только в `TrayIcon.cs`, через `using Forms = System.Windows.Forms;`.

## Ключевые технические решения

**Оверлей — layered-окно, не хук.** `WindowStyle=None` + `AllowsTransparency=true` +
P/Invoke `SetWindowLong(GWL_EXSTYLE, WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE)`.
Инъекция DLL / хук DXGI **запрещены** — EAC, BattlEye, Vanguard, FACEIT дают за это бан.
Для exclusive fullscreen — только RTSS shared memory (он в белых списках античитов).

Borderless-игра перехватывает Z-order → `DispatcherTimer` раз в 1.5 с зовёт
`SetWindowPos(HWND_TOPMOST, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE)`.
`SWP_NOACTIVATE` обязателен, иначе игра вылетает из фокуса каждый тик.

**Управление оверлеем — только хоткеи.** Окно сквозное по построению, мышью его
не подвинуть и не нажать. `RegisterHotKey` на HWND главного окна + `WM_HOTKEY`
через `HwndSource.AddHook`. Флаг `MOD_NOREPEAT` обязателен — без него зажатая
клавиша шлёт поток событий. Комбинации: Ctrl+Alt+O — вкл/выкл, Ctrl+Alt+1…4 — углы.
Занятую другим процессом комбинацию `RegisterHotKey` просто не даёт — это штатно,
пишем предупреждение в лог и работаем дальше.

**Настройки применяются мгновенно.** Каждый контрол `SettingsWindow` подписан на
изменение → `SaveToSettings` + `Save()` + `_onApply()`. Кнопки «Применить» нет.
Два обязательных условия, без которых это ломается:
- флаг `_loading` на время первичной расстановки контролов — иначе события
  расстановки затирают настройки полусобранными значениями;
- снимок `AppSettings.Clone()` при открытии окна; «Вернуть как было» зовёт
  `CopyFrom(snapshot)`. Именно `CopyFrom`, а не подмена ссылки: экземпляр
  `AppSettings` уже роздан главному окну и оверлею.

**Разметка оверлея — `Grid.IsSharedSizeScope` + `SharedSizeGroup`.** Колонка подписей
общая для всех строк; жёсткая ширина ломалась при смене размера шрифта и на длинных
подписях вроде «Потери шлюз».

**ICMP не требует админа.** `System.Net.NetworkInformation.Ping` — обёртка над
`IcmpSendEcho2`, не над raw-сокетами. Traceroute через `PingOptions.Ttl` — тоже без админа.

**UDP remote-адрес — только через ETW.** `GetExtendedUdpTable` remote-адрес не отдаёт,
это тупик. Провайдер `Microsoft-Windows-Kernel-Network`, события `UdpIpSend`/`UdpIpRecv`.
Требует прав администратора → манифест поднимается до `requireAdministrator` только
на этапе 3, не раньше.

**Тайминги.** `PeriodicTimer` + `Stopwatch`. `System.Timers.Timer` неточен и не годится.
Штатное разрешение таймера Windows 15.6 мс — для тика 250 мс достаточно,
`timeBeginPeriod` не трогаем.

**Графики.** Только `DataStreamer`/`DataLogger` из ScottPlot 5 — они рассчитаны на
скользящее окно. Пересоздание `Scatter` на каждом тике — главная причина тормозов
самодельных realtime-графиков, так не делать.

Три вещи про `DataStreamer` 5.1.59, каждая стоила отладки:

- **Значение под курсором он не отдаёт.** Держим своё зеркало данных
  (`Ring` в `MainWindow`) и читаем из него.
- **Координата X — это номер слота в буфере (0…Capacity)**, а точки прижаты
  к правому краю. Индекс считается как `round(xData) − (Capacity − Count)`.
  Считать через долю оси нельзя: при неполном буфере и при зуме промахивается.
- **`ManageAxisLimits` переустанавливает пределы осей на каждой отрисовке.**
  На время зума его надо выключать, иначе ось возвращается на место мгновенно
  и увеличение выглядит несработавшим. Пропустить только свой `AutoScale()` мало.

**Зум графиков — свой.** `UserInputProcessor.Disable()`, выделение рисуем WPF-овским
`Rectangle`, пределы ставим через `Axes.SetLimits`, сброс — двойным кликом.
После любой смены осей курсорный слой надо прятать явно: он не пересчитывается,
пока мышь не двинется, и остаётся висеть с неверным значением.

**Буферы.** В памяти: пинг 2400 точек (10 мин × 4 Гц), системные метрики 300 (5 мин × 1 Гц).
Полная история — в SQLite (этап 6).

## Сборка и поставка

```powershell
dotnet build "C:\Users\Admin\project claude\app_lan\NetAudit\NetAudit.slnx"
.\release.ps1 -Version X.Y.Z -Notes "..."   # publish + zip + установщик + version.json
```

`publish.ps1`, `install.bat`/`install.ps1`, `sign-setup.ps1` — старые названия,
все три давно удалены (см. «Установка: install.bat блокировался Application
Control» и «Git и обновления» ниже), их функции поглотил `release.ps1` и
`installer/NetAudit.iss`. **Без `PublishReadyToRun`** — убран 2026-08-25 (см.
раздел про блокировку установщика SAC): нативный код в managed dll подпадает
под более строгую проверку Smart App Control, чем обычная управляемая сборка.

Поставка: `dist\NetAudit-vX.Y.Z-win-x64.zip` (framework-dependent, портативная)
и `dist\NetAudit-Setup-vX.Y.Z.exe` (Inno Setup, ставит в Program Files и заводит
задачи в Планировщике — см. «Установленная копия всегда запускается повышенно»).
Настройки живут в `%LOCALAPPDATA%\NetAudit\settings.json`, при обновлении
сохраняются. Версия объявляется в трёх местах и они должны совпадать:
`NetAudit.App.csproj`, `release.ps1` (параметр `-Version`), `version.json`.

## Потребление ресурсов (замерено 2026-08-17)

Итог: **≈6,5% одного ядра** в установившемся режиме со всеми включёнными
функциями, ~163 МБ рабочего набора. До оптимизации было 16–20%.
Первые 10–15 секунд после запуска расход выше (JIT, опрос железа, засев
счётчиков) — мерить надо после прогрева, иначе получите 12% и обманетесь.

Что и сколько стоило, по изолированным замерам:

| Источник | Было | Стало | Как починено |
|---|---|---|---|
| `GpuProbe` | 110–120 мс/тик = **12% ядра** | 1,7 мс = 0,2% | один `ReadCategory()` вместо 108 счётчиков |
| Отрисовка 5 графиков | **+12,1%** | в пределах шума | цикл перерисовки 20 Гц → 2 Гц |
| Лог, все строки | **+10,0%** | +3,4% | строки копятся и отдаются в UI пачками |
| `WifiProbe` (netsh) | 131 мс/5 с = **2,6%** | 0 на кабеле | проверка наличия Wi-Fi адаптера до запуска процесса |
| Опрос процессов | 12 мс/2 с = 0,6% | 0, если вкладка закрыта | пропуск, когда диспетчер не открыт |

**Ключевые уроки, чтобы не наступить снова:**

- Категория «GPU Engine» содержит экземпляр на процесс и движок — на этой машине
  408 штук, из них 108 с `engtype_3D`. Отдельный `PerformanceCounter` на каждый
  и `NextValue()` в цикле — это сотня миллисекунд на тик. Правильно —
  `PerformanceCounterCategory.ReadCategory()` один раз и свои дельты через
  `CounterSampleCalculator`.
- **`ReadCategory()` отдаёт имена экземпляров в нижнем регистре**, в отличие от
  `GetInstanceNames()`. Сравнение обязано быть регистронезависимым, иначе
  не совпадёт ничего и GPU будет молча показывать 0%.
- `ScrollIntoView` на каждой строке лога заставляет список пересчитывать
  разметку. При восьми строках в секунду это дороже всех сетевых проб вместе.
- Запуск `netsh` — это создание процесса, 130 мс. Проверить наличие
  беспроводного адаптера через `NetworkInterface` стоит доли миллисекунды.

Мерить так: отсечь первые 15 секунд, брать `TotalProcessorTime` за 20–30 секунд,
повторить трижды и взять медиану. Машина под фоновой нагрузкой даёт разброс ±3%.

## Тема оформления

Единая тёмно-зелёная тема — `NetAudit.App/Theme.xaml`, подключается через
`App.xaml`. Палитра объявлена там же (`ClrBase`, `Accent`, `Good`, `Warn`, `Bad` и т.д.),
хардкодить цвета в окнах не нужно.

**Почему шаблоны, а не Setter'ы.** Стандартные шаблоны WPF рисуют выпадающий
список `ComboBox`, вкладки `TabItem`, поля ввода, флажки и подсказки светлой
системной темой. Задать им `Background` бесполезно: белый фон приходит из
шаблона, а у `ComboBox` он вообще в отдельном `Popup`. Поэтому в теме именно
`ControlTemplate`.

Три грабли, каждая проверена на живом приложении:

- **`Stroke` требует Brush, а не Color.** `Stroke="{StaticResource ClrBase}"`
  роняет приложение при разворачивании шаблона (`XamlParseException`), причём
  не при старте, а в момент первой отрисовки контрола. Использовать `BgBase`.
- **`ContentPresenter` в шаблоне `TabControl` обязан называться
  `PART_SelectedContentHost`.** Без имени вкладка рисуется правильно, но
  содержимое выпадает из дерева автоматизации: UIA перестаёт видеть все
  контролы внутри вкладок.
- **Локальные `Window.Resources` с неявными стилями перекрывают тему.** Стиль
  `<Style TargetType="Button">` без `Template` в окне возвращает системный
  шаблон и светлый вид. В окнах локальные стили не держим.

Серии графиков: шлюз `#4FD98B`, интернет `#86D97A`, приём `#5CD1C0`,
отдача `#86D97A`, CPU `#E3B44F`, RAM `#D4E8A8`.

## Smart App Control и подпись (важно, проверено 2026-08-17)

На этой машине **Smart App Control включён** —
`HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy` → `VerifiedAndReputablePolicyState = 1`.
Он и есть источник сообщений «приложение частично заблокировано».
Блокировки видны в журнале `Microsoft-Windows-CodeIntegrity/Operational`,
события **3077 / 3033 / 3118**.

Измерено запусками, не по документации:

| Что | Запусков успешно | Блокировок SAC |
|---|---|---|
| dll и exe без подписи | 4 из 4 | 0 |
| dll и exe с самоподписанным сертификатом | 0 из 3 | каждый запуск |
| exe самоподписан, dll без подписи (как делает `publish.ps1`) | 3 из 3 | 0 |

**Правило: не подписывать `NetAudit.App.dll` самоподписанным сертификатом.**
SAC признаёт только сертификаты из своего списка и облачную репутацию; локальное
доверие к сертификату (Root, TrustedPublisher) он **не учитывает**. Неподписанную
управляемую dll он пропускает по репутации, а подписанную недоверенным издателем —
отвергает. То есть самоподписанная подпись dll делает строго хуже, чем её отсутствие.

`publish.ps1` подписывает только exe — это корректно, менять нельзя.
Автоподпись обычных сборок в csproj пробовали и откатили, комментарий с причиной
оставлен прямо в `NetAudit.App.csproj`.

Полностью снять предупреждения могут только два пути, оба вне кода:
отключить Smart App Control (**необратимо**: обратно включается лишь переустановкой
Windows) либо купить коммерческий сертификат подписи. Это решение владельца.

### Жёсткий блок из-за метки «Интернет» (Mark of the Web), не самого файла (2026-08-20/21)

Через день после первого релиза v1.1.0 сам владелец словил **жёсткую блокировку
без кнопки «Всё равно запустить»** — окно «Приложение заблокировано», ровно то,
за что отвечает SAC (в отличие от SmartScreen, у SAC нет кнопки обхода вообще).
Заблокирован был не собранный локально exe, а **`NetAudit.App.exe`, распакованный
из скачанного с GitHub `NetAudit-v1.1.0-win-x64.zip`** — то есть ровно тот путь,
которым идёт обычный пользователь.

Причина оказалась не в отсутствии репутации у нового бинарника (как можно было
подумать), а в **Zone.Identifier (Mark of the Web)**: у заблокированного файла
`Get-Content -Stream Zone.Identifier` отдавал `ZoneId=3` (зона «Интернет»).
Проверено эмпирически прямо на этом файле: `Unblock-File` (снимает поток
Zone.Identifier) — и exe запустился с первого раза, без единого предупреждения.
Это правит и уточняет измерение от 17.08 в таблице выше: «unsigned = всегда
проходит» было верно только для файлов **без метки Интернета** (собранных или
скопированных локально). С меткой — тот же неподписанный exe блокируется жёстко.

**Уточнение 2026-08-25: гипотеза про иммунитет установщика опровергнута.**
Владелец словил тот же самый жёсткий блок («Приложение заблокировано», без
кнопки обхода) на скачанном с GitHub `NetAudit-Setup-v1.1.0.exe` — то есть
на самом установщике, а не на файлах, которые он распаковывает. Разбор
ошибки в прежнем рассуждении: правда, что Inno Setup пишет файлы *внутри себя*
через `CreateFile`, минуя проводник, и они не наследуют Zone.Identifier —
но это не имеет значения, потому что SAC блокирует **сам `.exe` установщика
целиком, до того как он успевает хоть что-то распаковать**. А Zone.Identifier
на сам установщик ставит не проводник (это было верно только для распаковки
zip), а **сам браузер в момент скачивания** — это общий механизм Attachment
Execution Service, который помечает меткой «Интернет» вообще любой скачанный
файл, будь то zip или отдельный exe. Zip и установщик в этом смысле абсолютно
равноправны: оба нарываются на блок сразу после скачивания браузером, если
Smart App Control включён и файл не подписан доверенным сертификатом.
Проверено: скачанная через `gh release download` (не браузером) копия того же
установщика Zone.Identifier не получает и не блокируется — что подтверждает
причину именно в способе скачивания, а не в содержимом файла.

**Практический вывод: установщик не спасает от этой проблемы**, вопреки
более ранней гипотезе в этом файле. Единственный код-независимый выход —
см. раздел выше (отключить SAC или подписать сборку платным сертификатом).
До тех пор пользователю в любом случае придётся снимать метку вручную —
что с zip, что с установщиком.

**Практический совет пользователю, если Windows заблокировала exe без кнопки
обхода:** правой кнопкой по файлу → Свойства → внизу галочка «Разблокировать» →
OK. Либо `Unblock-File путь\к\NetAudit.App.exe` в PowerShell. Это не обходит
защиту нелегально — снимает ровно ту метку, из-за которой Windows решила
перепроверять файл построже, и Windows Defender всё равно продолжает
сканировать файл на вирусы как обычно.

### Установщик блокируется SAC независимо от MOTW — два разных бага в одной сессии (2026-08-25)

Владелец поставил v1.1.0 (портативный exe уже разблокирован вручную раньше),
и на первом же запуске после установки поймал новый краш:

```
Could not load file or assembly 'C:\Program Files\NetAudit\Microsoft.Diagnostics.FastSerialization.dll'.
Политика управления приложениями заблокировала этот файл. (0x800711C7)
```

**Причина 1 — ReadyToRun.** `release.ps1` собирал релиз с `-p:PublishReadyToRun=true`
(нативный код, вкомпилированный в managed dll ради быстрого холодного старта).
Сравнение файлов: `Microsoft.Diagnostics.FastSerialization.dll` — 184 320 байт
с R2R против 76 088 байт как чистый IL. Нативный код внутри управляемой dll
подпадает под ту же строгую проверку SAC, что и обычный native-exe:
журнал `Microsoft-Windows-CodeIntegrity/Operational`, события 3077/3033/3118,
текст «did not meet the Enterprise signing level requirements» — принципиально
другая, более строгая планка, чем репутационная проверка, которую проходит
обычная управляемая сборка (`NetAudit.App.dll`/`.exe` без R2R). **Исправлено:**
`-p:PublishReadyToRun=true` убран из `release.ps1` насовсем — выигрыш в скорости
старта WPF-приложения не стоит этого риска.

**Причина 2 — сам установщик Inno Setup, отдельная и более фундаментальная
проблема.** Собрали тестовый релиз 1.1.1 без R2R, владелец попытался запустить
`NetAudit-Setup-v1.1.1.exe` **прямо из локальной папки `dist`, без единого байта
метки «из интернета»** — и `explorer.exe` всё равно получил тот же блок
(события 3077/3033, тот же Policy ID, тот же текст про Enterprise signing
level). Это доказывает: гипотеза «установщик блокируется только из-за
Zone.Identifier» (раздел выше) была неполной. **Настоящая причина глубже:
установщик Inno Setup — это полностью нативный (не .NET) exe без цифровой
подписи**, и такие SAC всегда проверяет по строгой планке подписи, а не по
мягкой репутационной, которую как-то проходит apphost-обёртка `.NET`-приложения
(вероятно за счёт того, что структура .NET apphost чрезвычайно распространена
и узнаваема моделями репутации, а обёртки Inno Setup статистически чаще
используются вредоносным ПО для доставки полезной нагрузки). MOTW делает
блокировку ещё более вероятной, но не является необходимым условием — это
подтверждено экспериментом на этой же машине.

**Практический вывод: для установщика (в отличие от портативного zip) нет
даже обходного пути через Unblock-File** — диалог SAC для него в этой сессии
не предлагал вообще никакой кнопки продолжения ни разу, при любом источнике
файла. Единственный настоящий выход — доверенная подпись или отключение SAC.

**План на подпись: SignPath Foundation.** Бесплатная подпись кода для
open-source (OV-сертификат, управляемый пайплайн, поддерживает ручную
загрузку артефакта — не обязателен CI/CD). Требует лицензию, одобренную
OSI — из-за этого лицензия сменена на GPL v3 (см. раздел «Лицензия» выше).
Подача заявки и весь дальнейший процесс (создание Artifact Configuration,
интеграция) — ещё не сделаны, следующий шаг сессии.

## Счётчик FPS через ETW (2026-08-17)

Кадры считаются по событиям Present провайдеров `DXGI` (`CA11C036-0102-4A2D-A6AD-F03CFED5D3C9`)
и `D3D9` (`783ACA0A-790E-4D7F-8451-AA850511C6B9`) — тот же способ, что у PresentMon
от Microsoft. **Никаких хуков и внедрения в процесс игры** — сеанс ETW читает то,
что Windows и так публикует сама.

Цена: `TraceEventSession` может создать только администратор — это ограничение
самого ETW, не наше. Поднимать всё приложение до `requireAdministrator` ради
одной строки в оверлее неправильно (правило 4), поэтому:
- без прав `FpsProbe.Start()` тихо не срабатывает, `Available = false`, строка
  в оверлее показывает прочерк;
- кнопка «Счётчик FPS: состояние» во вкладке тестов объясняет причину и
  предлагает перезапуск через `Verb = "runas"`, если пользователь захочет.

`Source.Process()` блокирующий — крутится в своём `Thread`, не в `Task`.
`StopOnDispose = true` на сеансе закрывает его при штатном выходе — но
**только** при штатном. Подробности осиротевшего сеанса и второго найденного
бага — ниже.

Охват — Direct3D 9/10/11/12. Игры на Vulkan/OpenGL мимо DXGI не увидены.

**Найден и исправлен реальный баг (2026-08-17): счётчик всегда показывал прочерк.**
`_session.Source.AllEvents` — «сырая» подписка на события ETW без разбора манифеста.
Для DXGI/D3D9 их манифест зарегистрирован в системе через `wevtutil` (путь TDH),
а не разослан динамически по самой трассе ETW — а именно динамический путь
понимает `Source.AllEvents`. В результате `ev.TaskName` приходил как
`"EventID(42)"`, а не `"Present"`, фильтр по имени не находил вообще ничего,
`Available` при этом был `true`, никакой ошибки — просто событий с нужным
именем не приходило никогда. Лечится подпиской через
`Microsoft.Diagnostics.Tracing.Parsers.RegisteredTraceEventParser`, который
резолвит manifest-провайдеров через TDH правильно:
```csharp
var parser = new RegisteredTraceEventParser(session.Source);
parser.All += OnEvent;   // вместо session.Source.AllEvents += OnEvent
```
Заодно исправлена вторая ошибка, которая проявилась бы сразу после первой:
фильтр был `TaskName.Contains("Present")`, а у DXGI три разных события с
«Present» в имени — `Present` (id 42/43, то, что нужно), `IDXGISwapChain_Present`
(id 178/179, вызов метода приложением) и `PresentMultiplaneOverlay` (id 55/56).
При рабочем резолвинге имён Contains утроил бы счётчик. Заменено на точное `== "Present"`.

**Проверено эмпирически на живой Dota 2** — с элевацией через UAC (deny-only
admin token на этой машине даёт токен без видимого промпта; `Start-Process
-Verb RunAs` элевирует молча). Отдельный консольный инструмент с той же
логикой, что в `FpsProbe`, насчитал 526 кадров за 10 секунд = 52,6 FPS —
правдоподобное число. Пары id 42/43 сошлись 1:1, что подтверждает точность подсчёта.

Диагностика на будущее: `FpsProbe.EventsSeen`/`PresentsMatched` прокинуты через
`SystemMetricsScheduler` в кнопку «Счётчик FPS: состояние» — если разрешение
имён снова сломается, будет видно число полученных событий против опознанных
кадров, а не только глухой прочерк.

**Второй найденный баг (2026-08-17): счётчик работал один раз и потом навсегда
пропадал.** Сеанс ETW живёт в ядре Windows и переживает породивший его
процесс. `StopOnDispose` закрывает сеанс только при штатном `Dispose()` —
при аварийном завершении (падение, `Stop-Process`, выключение питания)
сеанс `NetAudit-FPS` остаётся висеть в системе до перезагрузки. Следующий
запуск создаёт `TraceEventSession` с уже занятым именем: **без единой
ошибки**, `Available` становится `true`, но `Source.Process()` никогда не
получает событий — сеанс существует, но не тот, в который что-либо пишется.

Воспроизведено пошагово: `Stop-Process` живого счётчика → `logman query -ets`
подтверждает осиротевший `NetAudit-FPS` → перезапуск приложения даёт
«Кадры —» → ручной `logman stop NetAudit-FPS -ets` → следующий перезапуск
сразу считает кадры. Лечится тем, что `FpsProbe.Start()` перед созданием
своего сеанса сначала проверяет `TraceEventSession.GetActiveSessionNames()`
и, если сеанс с таким именем уже есть, подключается к нему
(`new TraceEventSession(SessionName, TraceEventSessionOptions.Attach)`)
и останавливает:
```csharp
if (TraceEventSession.GetActiveSessionNames().Any(n => n == SessionName))
{
    using var stale = new TraceEventSession(SessionName, TraceEventSessionOptions.Attach);
    stale.Stop();
}
```
Добавлено `FpsProbe.LooksDead` — сеанс поднят дольше 15 секунд, а событий
`EventsSeen` всё ещё ноль. Это ровно то состояние, в котором баг проявлялся:
формально «работает», фактически мёртв. Диагностика теперь различает эти
два случая, а не показывает одинаковое «работает» в обоих.

Проверено регрессией на реальном install/uninstall цикле собранного
установщика v1.0.5: жёсткое убийство elevated-процесса → осиротевший
сеанс подтверждён `logman` → повторный запуск через задачу в Планировщике →
сеанс снят и создан заново автоматически → «Кадры 52» с первого раза,
без ручного вмешательства.

## Игровой режим и распознавание полноэкранных окон (2026-08-17)

`GameModeDetector.Detect()`: сначала `SHQueryUserNotificationState` (ловит
эксклюзивный Direct3D), затем geometry-проверка окна переднего плана против
`MonitorFromWindow`/`GetMonitorInfoW` (ловит borderless).

**Геометрии одной недостаточно.** Развёрнутое обычное окно занимает монитор
не хуже игры — замерено: проводник и Chromium в развёрнутом виде дают
1936×1096 при мониторе 1920×1080, с запасом перекрывая его. Если панель задач
скрывается автоматически, рабочая область совпадает с монитором и отличить
их геометрией уже нельзя. Без дополнительной проверки NetAudit уходил в
игровой режим от развёрнутого браузера и не возвращался.

Признак настоящей игры — отсутствие `WS_CAPTION` в стиле окна (`GetWindowLong(GWL_STYLE)`).
У браузера, проводника, терминала заголовок в стиле окна есть всегда, даже
когда сам заголовок нарисован приложением поверх системной рамки. У игры
в полноэкранном режиме (exclusive и borderless) заголовка нет — она рисует
кадр во весь экран сама. Дополнительно отсекаются известные процессы оболочки
(`explorer`, `TextInputHost`, `ShellExperienceHost` и т.д.) — у них тоже
бывают безрамочные окна во весь экран.

Переключение режима — только после двух одинаковых наблюдений подряд
(`FlipThreshold = 2`, тик раз в 2 с). Без этого alt-tab между игрой и
чем угодно ещё дёргал бы приоритет процесса каждые две секунды.

Что урезается в игровом режиме и что нет — см. `MainWindow.GameMode.cs`.
Частота пинга **не трогается никогда**: это единственное, ради чего
приложение вообще работает во время игры.

## Обновление и установка (2026-08-17)

Автообновление не может переписать собственный exe, пока процесс работает.
Поэтому `UpdateInstaller.DownloadAsync` только скачивает и распаковывает во
временную папку, а подмену файлов делает отдельный PowerShell-скрипт
(`ApplyAndRestart`), который:
1. ждёт завершения процесса по PID (до 30 с);
2. делает резервную копию текущей папки установки;
3. копирует новые файлы; при сбое копирования восстанавливает из резервной копии;
4. запускает обновлённый exe.

**Контрольная сумма обязательна для доверия.** Ссылка на архив приходит из
`version.json` по обычному HTTP(S) без дополнительной защиты — если её не
проверять, подменённый на пути архив выполнился бы от имени пользователя без
единого предупреждения. `release.ps1` считает SHA-256 и кладёт в `version.json`
автоматически; без него `UpdateInstaller` не отказывает намертво, но явно
предупреждает и показывает посчитанную сумму, чтобы решение осталось за
пользователем.

**Проверено эмпирически, трижды подряд, на настоящих релизах** (1.0.0→1.0.1,
1.0.1→1.0.2, 1.0.2 против самого себя). Нашлись два реальных бага:

1. **Версия сборки зависала на 1.0.0.** `NetAudit.App.csproj` явно задавал
   `<AssemblyVersion>1.0.0.0</AssemblyVersion>` и `<FileVersion>1.0.0.0</FileVersion>`
   константой — а `-p:Version=$Version` при publish переопределяет только
   `<Version>`, не трогая уже явно заданные `AssemblyVersion`/`FileVersion`.
   `Assembly.GetName().Version` (на нём стоят заголовок окна и сравнение версий
   в `UpdateChecker`) навсегда оставался 1.0.0.0, хотя файлы на диске обновлялись
   верно — после обновления 1.0.0→1.0.1 приложение продолжало предлагать
   «доступно 1.0.1», как будто её ещё не поставили. Лечится удалением явных
   тегов — без них SDK сам выводит оба поля из `<Version>`.
2. **Подмена файлов не убирала лишнее.** `Copy-Item -Recurse -Force` копировал
   новые файлы поверх старых, но не удалял то, чего в новом релизе больше нет —
   `install.bat`/`install.ps1`, убранные в 1.0.1, продолжали лежать на диске
   после «обновления». Лечится очисткой папки перед копированием
   (`Get-ChildItem $to | Remove-Item -Recurse -Force`, потом `Copy-Item`).

**Важный нюанс самообновления**, не баг, а свойство механизма: фикс №2
подействовал не сразу. Обновление 1.0.1→1.0.2 выполнялось кодом ещё старой,
не чистящей версии — саму подмену файлов делает `UpdateInstaller`, который
СЕЙЧАС установлен, а не тот, что скачивается. Реально проверено: 1.0.1→1.0.2
не почистило install.bat/.ps1, но `FileVersion` сразу стал верным 1.0.2.0 —
эта часть фикса вшита в метаданные самого exe-файла при сборке и не зависит
от того, чей код его копировал. Следующий цикл обновления (уже с версии 1.0.2)
чистит корректно. Из этого следует общее правило: **бажный `UpdateInstaller`
чинится только на одно поколение позже**, поэтому баги в самом механизме
обновления особенно дорого стоят и требуют лишней осторожности при правке.

## Git и релизы (2026-08-17)

Репозиторий: `app_lan/` целиком, ветка `main`. `.gitignore` режет `bin/`, `obj/`,
`dist/`, сертификаты (`*.pfx`, `*.snk`, `NetAudit-cert.cer`) и
`**/.claude/settings.local.json` — с двумя звёздочками, потому что такой файл
есть и в `app_lan/.claude/`, и в `NetAudit/.claude/`, а путь с одной чертой
привязывается только к папке самого `.gitignore`.

`.gitattributes` держит LF в репозитории и CRLF на диске для `.ps1`/`.bat`/`.cmd` —
PowerShell 5.1 читает скрипт с диска, а не через git, и на «чужом» переводе
строки (в связке с отсутствием BOM) уже один раз калечил кириллицу.

`release.ps1` — новый скрипт для выкладки, `publish.ps1` остаётся для быстрой
локальной сборки без счётчика SHA-256. Различие принципиальное: `release.ps1`
обязан обновить `version.json` контрольной суммой, иначе `UpdateInstaller`
не сможет доверять скачанному архиву.

**Публичный релиз собирается без подписи.** `release.ps1` по умолчанию не
подписывает exe — только с флагом `-Sign`, и то тогда сертификат и
`trust-cert.ps1` кладутся в архив, иначе доверять нечему. Причина решения —
то же измерение SAC, что и выше по файлу: самоподписанный exe без локального
доверия блокируется жёстче неподписанного. Случайный человек из интернета
сертификат никогда не доверяет заранее, значит для публики подписывать вредно,
а не полезно. Первым багом на эту тему было то, что скрипт подписывал exe,
но не вкладывал сертификат в архив — то есть отдавал ровно ту комбинацию,
которая измеренно хуже отсутствия подписи. Исправлено до первого релиза.

Репозиторий: `github.com/limbo-wh/netaudit`, публичный. Локальная git identity
задана прямо в этом репозитории (`git config user.name/email` без `--global`),
потому что на машине несколько разных GitHub-аккаунтов под разные проекты.
`gh` CLI поставлен через `winget install GitHub.cli` и авторизован
device-flow'ом (`gh auth login --web`) — раньше на машине его не было.

**Важный урок про `main` и релизы (2026-08-20).** Владелец обнаружил, что новые
пользователи, скачавшие установщик с GitHub, не видели тумблер бета-обновлений —
`version.json`/установщик в последнем релизе (1.0.6, 17.08) физически устарели.
Причина: несколько коммитов подряд шли в `dev` (хоткеи, лицензия, ветки, беты,
single-instance, температура, RAM-кэш, порядок метрик), `dev` сливался в `main`,
но **`release.ps1` для стабильного канала после 1.0.6 ни разу не запускался** —
GitHub Release с реальными файлами не появлялся, только код в репозитории.
Слитый в `main` код и опубликованный релиз — разные вещи, путать нельзя.
**Правило на будущее: после `git merge dev` в `main` обязательно гнать
`release.ps1` и `gh release create`, иначе главная ветка и то, что видят
пользователи через автообновление, расходятся молча.**

Выпущен v1.1.0 (2026-08-20) — `release.ps1 -Version 1.1.0`, установщик и zip
через `gh release create`, `version.json` в `main` указывает на него.

## Установщик убран: .bat блокируется целиком (2026-08-17)

`install.bat` (двойным щелчком поднимал `powershell.exe -ExecutionPolicy Bypass
-File install.ps1`) на файле, помеченном как «загружено из интернета»
(Zone.Identifier — ставит любой браузер), блокировался Application Control
насмерть: **«An Application Control policy has blocked this file. Dangerous
file extension from the web.»** Воспроизведено на этой машине искусственной
меткой зоны через `Set-Content -Stream Zone.Identifier`. Это не про подпись
и не про репутацию — блокируется само расширение `.bat`/`.cmd` у файла из
интернета, вне зависимости от содержимого. Проверено: тот же файл с
расширением `.ps1`, запущенный явно (`powershell -File`), и сам `.exe`
с той же меткой — запускались нормально.

Решение — не чинить `.bat`, а убрать его функции целиком:
- Собранный exe — framework-dependent (`--self-contained false`). Если .NET
  Desktop Runtime не установлен, **сам apphost** показывает нативный диалог
  со ссылкой на официальную страницу загрузки Microsoft — это встроенное
  поведение .NET, не код NetAudit, и ничем не блокируется.
- Ярлык на рабочем столе создаёт сам процесс: `NetAudit.App/DesktopShortcut.cs`,
  `WScript.Shell` через позднее связывание (`Type.GetTypeFromProgID` +
  `dynamic`), без вызова внешнего интерпретатора. Баннер на первом запуске
  (`ShortcutBanner` в `MainWindow.xaml`, флаг `AppSettings.ShortcutOffered`
  чтобы не спрашивать дважды) плюс постоянная кнопка на вкладке тестов.

`install.bat`, `install.ps1` и дублировавший `release.ps1` `publish.ps1`
удалены из репозитория. `trust-cert.ps1` остался — он нужен только для
`-Sign`-сборок. Ниже (раздел «Полноценный установщик») — почему установщик
всё же вернулся, но уже не батником, а через Inno Setup, и что он решает
такого, чего batch-скрипт решить не мог в принципе.

## Полноценный установщик: Inno Setup + Планировщик заданий (2026-08-17)

`NetAudit\installer\NetAudit.iss`, собирается компилятором `ISCC.exe`
(Inno Setup 6, `winget install JRSoftware.InnoSetup`). Не путать с убранным
выше `install.bat` — это не batch-скрипт, поднимающий `powershell.exe
-ExecutionPolicy Bypass`, а полноценный `Setup.exe`, который Windows не
считает «опасным расширением из интернета» (то расследование касалось
конкретно `.bat`, не установщиков вообще).

Версия передаётся снаружи: `ISCC.exe /DMyAppVersion=X.Y.Z NetAudit.iss`,
источник файлов — уже опубликованная `release.ps1` папка `dist\NetAudit-vX.Y.Z\`.
`release.ps1` сам вызывает `ISCC.exe`, если находит его по стандартным
путям; не находит — пропускает шаг с предупреждением, старый цикл (zip
без установщика) не ломается.

**Главное, ради чего всё затевалось: задача в Планировщике заданий, чтобы
счётчик FPS работал без запроса UAC при каждом запуске.** Владелец выбрал
именно этот вариант из трёх предложенных (обычный установщик / установщик
+ задача / просто напоминать в приложении).

Механизм (`installer/register-task.ps1`, вызывается из `[Run]` — сам
установщик уже elevated, поэтому создание задачи проходит без лишнего
запроса):
```powershell
$action    = New-ScheduledTaskAction -Execute $ExePath
$principal = New-ScheduledTaskPrincipal -UserId "$env:USERDOMAIN\$env:USERNAME" `
                                        -RunLevel Highest -LogonType Interactive
Register-ScheduledTask -TaskName $TaskName -Action $action -Principal $principal -Force
```
Дальше `schtasks /Run /TN "NetAudit (администратор)"` (или второй ярлык
в Пуск/на рабочем столе с тем же вызовом) поднимает процесс с повышенным
токеном — Планировщик заданий делает это как системная служба, в обход
обычного пути элевации через explorer.exe, и поэтому без диалога согласия.
Задокументированный, широко используемый приём для локального
администратора своей машины, не обход защиты.

**Проверено эмпирически, не на словах**: оба процесса, запущенные через
такую задачу, подтверждены как High integrity (`0x3000`) прямым чтением
токена процесса (`OpenProcessToken` + `GetTokenInformation(TokenIntegrityLevel)`),
а не по факту отсутствия UAC-окна — окна не бывает и при отклонённой
элевации, поэтому только явная проверка токена даёт достоверный ответ.

**Найдена и исправлена проблема с удалением.** `CloseApplications=yes`
в `[Setup]` (интеграция с Windows Restart Manager — просит закрыть
приложения, держащие файлы) сам по себе не освобождает все нативные
DLL: проверено — после него на диске осталось 13 из 16 файлов, процесс
остался жив. У WPF-приложения со SkiaSharp/ScottPlot часть библиотек
подгружается путём, который RM не отслеживает. Добавлен explicit-шаг
`pre-uninstall.ps1` первым в `[UninstallRun]` (выполняется до удаления
файлов — сами `.ps1` лежат в `{app}` до самого конца):
```powershell
Get-Process -Name "NetAudit.App" -ErrorAction SilentlyContinue | Stop-Process -Force
for ($i = 0; $i -lt 20; $i++) {
    if (-not (Get-Process -Name "NetAudit.App" -ErrorAction SilentlyContinue)) { break }
    Start-Sleep -Milliseconds 300
}
```
`Stop-Process` возвращается сразу после сигнала на завершение, а не после
того, как ОС отпустила дескрипторы — отсюда опрос вместо одной попытки.
После этого фикса деинсталляция прямо во время работы программы (не
закрывая её вручную) очищает файлы, задачу и процесс полностью — проверено
дважды, до и после фикса, с одинаковым сценарием.

Установщик — путь для тех, кто ставит новую копию через `Setup.exe`.
Для портативного zip остаётся прежний путь: `DesktopShortcut.CreateElevated`
внутри самого приложения (ярлык с флагом `RunAsAdmin` — UAC при каждом
запуске, в отличие от задачи в Планировщике, но не требует прав на этапе
установки).
`-Sign`-сборок узкому кругу машин, в публичный релиз не попадает.

## Разгон перед игрой: Game Boost (2026-08-18)

Одна кнопка на новой первой вкладке главного окна («🎮 Игровой режим»), хоткей
Ctrl+Alt+B, пункт в трее — все три дёргают `GameBoostService` (`NetAudit.Core/GameBoost/`).
Пять независимых твиков, каждый — сам по себе, без общей транзакции: если один
не применился, остальные всё равно выполняются, а в отчёт (`GameBoostReport`)
попадает и то, что удалось, и то, что пропущено.

- **План питания** — `powercfg /getactivescheme` / `/setactive <GUID>`.
  GUID «Высокая производительность» (`8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c`)
  зашит константой: схема есть в Windows всегда, даже если скрыта из панели
  управления. Смена активной схемы прав администратора не требует.
- **Уведомления Windows** — `HKCU\Software\Microsoft\Windows\CurrentVersion\
  PushNotifications\ToastEnabled` (DWORD). HKCU, элевация не нужна.
- **Визуальные эффекты** — `SystemParametersInfo(SPI_SETUIEFFECTS)` (0x103F),
  один вызов включает/выключает все эффекты разом, как «Настроить для
  наилучшего быстродействия» в Windows. Тоже без прав администратора.
- **Службы SysMain и WSearch** — единственный твик, которому нужны права.
  Обе останавливаются одним повышенным PowerShell (`Stop-Service -Name
  'SysMain','WSearch'`) — UAC спрашивается один раз на обе службы, а не по
  разу на каждую. По умолчанию выключен в настройках (`GameBoostStopServices
  = false`): единственный из пяти твиков, который реально трогает систему
  и требует подтверждения, остальные — обратимые косметические переключатели.
- **Приоритет процесса игры** — `AboveNormal`, применяется точечно: либо сразу
  по нажатию кнопки, если игра уже развёрнута, либо позже через интеграцию
  с `GameModeDetector` (`MainWindow.GameMode.cs`: `EnterGameMode`/`LeaveGameMode`
  зовут `BoostGameProcessPriority`/`RestoreGameProcessPriority`) — кнопку
  разгона нажимают обычно ДО запуска игры, когда процесса ещё нет.
- **Закрытие программ** — `CloseMainWindow`, не `Kill`: пользователь выбирает
  их сам из чек-листа реально запущенных окон (кнопка «Обновить список»),
  список хранится в `AppSettings.GameBoostCloseApps` между запусками.

**Откат после сбоя — тот же урок, что и с осиротевшей ETW-сессией FPS**
(см. выше): состояние для отката пишется в `%LOCALAPPDATA%\NetAudit\
gameboost-state.json` сразу после каждого применённого шага, а не только
хранится в памяти. Если процесс NetAudit упадёт или будет убит с включённым
разгоном, файл переживёт его, а твики в системе — тоже. При следующем
старте `RecoverGameBoostAsync` видит файл, откатывает всё записанное
(включая перезапуск служб, если они были остановлены — второй UAC-запрос
уже при следующем запуске NetAudit) и удаляет файл. При обычном выходе
через крестик/трей то же самое делает `Window_Closing` синхронно, до
остановки планировщиков.

Настройки авто-режима (`GameModeEnabled` и три подпункта) переехали с этой
вкладки — раньше жили в окне настроек, теперь там только автозапуск и трей.

## Мелкие доработки и два найденных бага (2026-08-18)

Настраиваемые хоткеи (Ctrl+Alt + выбор клавиши для всех шести действий),
список исключений из авто-игрового режима и баллон в трее при серии потерь
во время игры — все три на вкладке «Игровой режим». `HotkeyManager` получил
`Bind(slot, mods, vk, action)` вместо `Register`: повторный вызов с тем же
именем слота снимает старую комбинацию и ставит новую, поэтому смена хоткея
в настройках действует мгновенно через `MainWindow.RebindHotkeys()`
(вызывается и при старте, и из `ApplyAllSettings()`).

**Баг 1 — порча settings.json при каждом первом запуске.** Чекбоксы игрового
режима/разгона в `SetupGameBoost()` выставляются по одному, а обработчики
`Checked`/`Unchecked` висят с разметки XAML с самого создания контрола —
каждое присвоение `IsChecked = true` тут же вызывало обработчик, который
читал состояние ВСЕХ чекбоксов группы (включая ещё не выставленные, то есть
`false`) и сохранял в `_settings`. Следующая строка `SetupGameBoost()` читала
из `_settings` уже испорченное значение. Итог на новом `settings.json`:
`true` только у первого чекбокса в группе, у остальных — `false`, при
дефолте `true` в коде у всех. Нашлось не по догадке, а эмпирически: удалил
файл настроек, запустил заново, увидел порчу на диске. Лечение — флаг
`_gameTabLoading`, тот же приём, что `_loading` в `SettingsWindow` (там он
уже стоял с самого начала, здесь про него забыли). **Урок:** любой новый
экран с чекбоксами, которые выставляются программно ИЗ настроек и при этом
сами пишут обратно В настройки, обязан иметь такой флаг — иначе порча тихая
и незаметная без прямого сравнения дефолтов в коде с файлом на диске.

**Баг 2 — `DisplayMemberPath` на кастомном `ComboBox` показывал имя типа.**
`Theme.xaml` задаёт свой `ControlTemplate` для `ComboBox` через
`SelectionBoxItem`/`SelectionBoxItemTemplate` — стандартный WPF-путь, должен
уважать `DisplayMemberPath`. На практике с `ItemsSource` из массива
произвольного класса и `DisplayMemberPath="Label"` комбобокс показывал
`NetAudit.App.SettingsWindow+HotkeyKeyOption` целиком вместо буквы —
подтверждено точечным скриншотом окна настроек, а не предположением по коду.
Причина не выяснена (не более приоритетна, чем рабочий обход). Обошли уже
проверенным в этом же файле приёмом: явные `ComboBoxItem` с `Tag`,
как у `CmbFontSize`, вместо `ItemsSource`/`DisplayMemberPath`/`SelectedValuePath`.
**Вывод для будущего:** в этом проекте `ItemsSource` + `DisplayMemberPath` на
кастомизированных `ComboBox` нельзя считать проверенным — либо явные
`ComboBoxItem`, либо тест живым запуском со скриншотом, а не чтение XAML.

## Границы — не проверено эмпирически

- Поведение layered-оверлея поверх конкретных игр с античитами.
- Структура RTSS shared memory текущей версии (сверять с её SDK-папкой, не гадать).
- Потери ETW-событий под высоким pps.
- Wi-Fi API на Windows 11 24H2+: SSID/BSSID пустые без служб геолокации.
- IPv6-сценарии.
- Игровой режим на настоящем эксклюзивном fullscreen (проверено только на
  безрамочном имитаторе и на развёрнутых обычных окнах).
- Game Boost: только сборка и визуальный рендер вкладки проверены живым

  после kill-теста) не проверено — см. `[?]` в `tasks.md`.

## Ветки: main (стабильная) + dev (бета) (2026-08-19)

Владелец ведёт разработку в `dev`, переносит в `main` только когда готово.
`main` — то, что видят обычные пользователи через `version.json`; `dev` —
черновая ветка, из которой можно выпустить бета-версию для тех, кто явно
включил соответствующий тумблер.

Механика в `release.ps1` (флаг `-Beta`):
- пишет `version-beta.json` вместо `version.json` (оба лежат рядом в
  `NetAudit/`, разные файлы — не конфликтуют);
- тег и имена файлов релиза получают суффикс `-beta` (`v1.1.0-beta`), чтобы
  не столкнуться с обычным релизом той же версии;
- инструкция в конце скрипта подсказывает закоммитить в `dev`, а не в `main`,
  и создать `gh release` с флагом `--prerelease`.
- перед обычным (не-`-Beta`) релизом скрипт напоминает сначала
  `git merge dev` в `main`, если готовили там.

В приложении (`AppSettings.cs`): `UseBetaUpdates` (bool, default false) +
`UpdateCheckUrlBeta` (URL на `version-beta.json` в `dev`) +
`EffectiveUpdateCheckUrl` — вычисляемое свойство, переключает между
стабильным и бета-манифестом. Тумблер — чекбокс «Получать бета-обновления»
в `SettingsWindow.xaml`, секция «Обновления» под «Трей и автозапуск»,
подключён через уже существующий `_loading`-guard и `WireLiveApply` — тот же
паттерн, что и у остальных настроек в этом окне, не отдельная схема.

`EffectiveUpdateCheckUrl` помечено `[JsonIgnore]` — вычисляемое, хранить его
в `settings.json` не нужно, там только `UseBetaUpdates` и обе URL.

## Температура CPU/GPU (2026-08-20, ветка dev)

`TemperatureProbe` (`NetAudit.Core/Probes/`) на `LibreHardwareMonitorLib`. Библиотека
грузит свой драйвер ядра (WinRing0) для чтения MSR/SMBus — без прав администратора
не встаёт, `Available=false`, `Sample()` отдаёт `NaN`. Тот же класс требования, что
у счётчика FPS (`FpsProbe.IsElevated` переиспользуется как условие для инициализации,
отдельную проверку не заводили).

Выбор датчика: приоритетно «Package»/«Tctl»/«GPU Core» (сводный по всему кристаллу),
иначе максимум по всем датчикам температуры этого `IHardware` — для многодатчиковых
GPU это горячее ядро, а не усреднённое число.

**Проверено живьём на этой машине (AMD APU, встроенная Radeon Graphics)**: CPU-темп.
читается реально и меняется по тикам (59→54→61°C). GPU-темп. стабильно «—» — у этой
интегрированной графики LibreHardwareMonitor не даёт отдельного `HardwareType.GpuAmd`
с датчиком температуры. Это ограничение библиотеки/железа для APU, не баг — то же
честное вырождение в прочерк, что и у GPU-нагрузки при отсутствии `PerformanceCounter`
категории. **Не проверено** на машине с дискретной видеокартой — там `GpuTempC`
должен появиться, `[?]` в tasks.md.

Оверлей: строки «Темп. CPU»/«Темп. GPU» сразу под «Видеокарта» — владелец попросил
именно туда. Пороги цвета: CPU 70/85°C, GPU 75/85°C (типичные для гейминга — выше
второго порога троттлинг уже рядом). Тумблеры `OvShowCpuTemp`/`OvShowGpuTemp`
в настройках, тот же `_loading`-guard и `WireLiveApply`, что у остальных строк оверлея.

## Очистка кэша ОЗУ (2026-08-20, ветка dev)

Кнопка «Очистить кэш ОЗУ» на вкладке «Тесты и сервис» → `RamCacheService`
(`NetAudit.Core/Diagnostics/`). Освобождает список ожидания (standby list) —
страницы, которые Windows держит про запас на случай повторного использования,
не трогая память работающих программ. Тот же системный вызов, что у RAMMap
(«Empty → Standby List») и известной утилиты EmptyStandbyList.exe:
`NtSetSystemInformation(SystemMemoryListInformation, MemoryPurgeStandbyList)`.
Требует включения привилегии `SeProfileSingleProcessPrivilege` — она есть у группы
Administrators, но по умолчанию выключена в токене, включается на лету через
`AdjustTokenPrivileges`.

Элевация — тот же паттерн, что у `NetworkResetService`: один повышенный
PowerShell-скрипт (`Verb=runas`), не всё приложение целиком. Скрипт компилирует
на лету C#-тип с нужными P/Invoke через `Add-Type -Language CSharp` и вызывает его.

**Найден и исправлен реальный баг при первом живом тесте.** Компилятор за
`Add-Type -Language CSharp` в Windows PowerShell 5.1 — старый CodeDom/csc, не
понимает инлайновое объявление переменной под `out` прямо в вызове (`out IntPtr
token`, синтаксис C# 7). Падало с ошибкой компиляции «ожидалась )» на месте
объявления, привилегия не включалась, purge не выполнялся — но диагностировалось
только по логу `[ОШИБКА]`, не крашем: маска для будущего — **`Add-Type` в скриптах
этого проекта писать только под старый синтаксис C#** (`Type var; Foo(out var)`,
не `Foo(out Type var)`).

**Проверено дважды живьём, элевированным процессом**: реальный прирост свободной
памяти после очистки (например, 4018→4125 МБ), лог `[ОК] список ожидания очищен`
доходит и раскрашивается во вкладке тестов корректно.

## Передвигаемые метрики оверлея (2026-08-20, ветка dev)

Владелец попросил дать пользователю самому настраивать порядок строк в оверлее.
Оверлей мышью не подвинуть и не нажать — он сквозной по построению (см. раздел
про оверлей выше), поэтому перетаскивание живёт не на самом оверлее, а в окне
настроек: список чекбоксов «Метрики» стал `ListBox` с ручкой ⠿ у каждой строки,
перетаскивание меняет порядок и сразу применяется (тот же `ApplyLive`, что у
остальных настроек).

**Общий источник истины** — `OverlayMetrics.cs` (`NetAudit.App`): массив
`(Key, Label, Tooltip)` на все 12 метрик плюс `Normalize(order)`, которая чинит
сохранённый список — неизвестные ключи выкидывает, пропущенные (старый
settings.json без поля вовсе, или метрика новее сохранённого файла) дописывает
в конец в порядке по умолчанию. Используется и оверлеем (в каком порядке класть
`Grid`-строки в `MetricsPanel.Children`), и окном настроек (какие строки и с
какими подписями показать в `ListBox`).

`AppSettings.OverlayMetricOrder` — `List<string>` из ключей. Видимость по-прежнему
хранится отдельными `bool`-полями (`OvShowFps` и т.д.) ради читаемого
settings.json — не стали сводить в словарь. `SettingsWindow` держит внутренний
`ObservableCollection<MetricItem>` (ключ, подпись, tooltip, галочка), при
`SaveToSettings()` разбирает его обратно и в `OverlayMetricOrder`, и в
соответствующие `OvShowX` через маленький `switch` в обе стороны.

Перетаскивание — стандартный приём WPF (`PreviewMouseLeftButtonDown` запоминает
элемент → `PreviewMouseMove` за порогом `SystemParameters.MinimumHorizontal/
VerticalDragDistance` зовёт `DragDrop.DoDragDrop` → `Drop` находит `MetricItem`
по `DataContext` элемента под курсором и переставляет `ObservableCollection.Move`).
Оверлей просто пересобирает `MetricsPanel.Children` в новом порядке при каждом
`ApplySettings` — строк всего 12, частичный diff не нужен.

**Проверено живьём частично.** Надёжно подтверждено: `OverlayMetrics.Normalize` +
`OverlayWindow.ReorderRows` — вручную вписал в settings.json нарочно испорченный
порядок (несуществующий ключ `"Bogus"` вставлен, `"NetTx"` пропущен) и перезапустил
приложение: оверлей на скриншоте показал ровно заданный порядок, «Bogus» тихо
пропал, «↑ Отдача» (NetTx) корректно появился последним. Это и есть та часть,
которую пользователь увидит, если сохранённый файл настроек когда-нибудь разойдётся
с текущим списком метрик — сработала верно.

**Не подтверждено настоящим перетаскиванием мышью.** Пробовал автоматизировать
через `SendInput`/`mouse_event` — WPF не запустил `DragDrop.DoDragDrop` ни разу
за несколько попыток с разной геометрией и таймингом. Это известное ограничение
синтетического ввода для WPF drag-and-drop (компоновщик/DWM нередко теряет часть
синтетических `WM_MOUSEMOVE`, которые WPF ждёт для срабатывания порога), а не
обязательно баг кода — сам обработчик визуально стандартный и такой же, как в
типовых примерах WPF. **Требуется живая проверка настоящей мышью** — см. `[?]`
в tasks.md.

## Установленная копия всегда запускается повышенно (2026-08-25)

По просьбе владельца задача Планировщика («NetAudit (администратор)»), раньше
бывшая вторым необязательным ярлыком, стала единственным путём запуска для
установленных через инсталлятор копий. Манифест `NetAudit.App.exe` не менялся
(по-прежнему `asInvoker`) — сознательно: требовать администратора манифестом
означало бы UAC-запрос при каждом старте для всех, включая портативный zip,
где повышение вообще не нужно большинству. Вместо этого меняется только то,
через что установщик заводит точки входа.

Проблема с автозапуском: `schtasks /Run /TN` не принимает аргументы во время
запуска — то, с чем стартует процесс, зашито в саму задачу при регистрации.
Обычный ярлык и автозапуск в трей (`--tray`) хотят разные аргументы, значит
нужны две задачи, не одна. Решение: `register-task.ps1` получил необязательный
`-Arguments`, установщик регистрирует `NetAudit (администратор)` (без аргументов,
для ярлыков и запуска сразу после установки) и `NetAudit (автозапуск)`
(`--tray`, только для `StartupManager`). `StartupManager.Apply()` проверяет
существование второй задачи (`schtasks /Query`, прав не требует) и, если она
есть, пишет в HKCU команду через `schtasks /Run` вместо прямого пути к exe;
если задачи нет (портативная копия) — как раньше, напрямую.

Не проверено на живом запуске (агент не может сам пройти UAC) — `.iss`
скомпилирован Inno Setup без ошибок, `dotnet build` чист, установщик собран
и передан владельцу для проверки. См. `[?]` в `tasks.md`.

## Стресс-тест, чёрный ящик и отчёт о сбоях (2026-09-13)

Владелец купил бывший в употреблении компьютер и попросил две вещи: возможность
гонять стресс-тесты и сохранение логов на случай краха машины. Обе задачи об одном:
поймать неисправность, которая проявляется редко и уносит систему целиком.

### Чёрный ящик: запись, переживающая синий экран

`Core/Logging/BlackBoxRecorder.cs` — CSV-строка раз в секунду в
`%LOCALAPPDATA%\NetAudit\blackbox\session-*.csv`.

**Главное решение — `FileOptions.WriteThrough` плюс `Flush(flushToDisk: true)`
после каждой строки.** Обычный буферизованный лог теряет при синем экране ровно
тот кусок, ради которого он и ведётся. Проверено эмпирически: `Stop-Process -Force`
живого процесса — все строки до последней секунды остались на диске.

**Признак аварийного завершения — отсутствие маркера, а не наличие записи о сбое.**
Последней строкой штатно закрытого файла пишется `# сеанс закрыт штатно`. Нет
строки — сеанс оборвался. Спрашивать об этом Windows не нужно.

**Штатное выключение Windows — тоже штатный выход.** Без подписки на
`Application.SessionEnding` каждое нормальное выключение выглядело бы как краш.

**Различение «упал NetAudit» и «умер компьютер»** — по времени загрузки системы
(`DateTime.Now - TickCount64`) против времени последней записи.

Запись идёт из фонового потока планировщика метрик, **до** захода в UI-поток:
перед крахом интерфейс обычно уже висит.

### Стресс-тест: проверяется правильность, а не только скорость

`Core/Diagnostics/StressTest.cs`. В отличие от `SystemBenchTest` (замер скорости
за 20 секунд) здесь длительная нагрузка с **проверкой каждого результата**:
процессор считает блок с заранее известным ответом, память заполняется шаблонами
и сверяется обратно, накопитель перечитывается со сверкой. Исправное железо не
ошибается ни разу, поэтому одно расхождение — уже диагноз.

Потоки нагрузки — свои `Thread`, не `Task.Run`: все потоки пула во время теста
заняты. Троттлинг меряется по счётчику самого теста, а не опросом частоты: WMI
отдаёт её с задержкой и округлением. Тест останавливается сам при 95 °C.

**Самопроверка перед нагрузкой — обязательная часть теста.** Каждой сверке
сначала подсовываются заведомо неверные данные, и тест убеждается, что она их
замечает; не замечает — останавливается вместо того, чтобы отрапортовать «ошибок
нет». Причина прямая: исправное железо и сломанная проверка дают снаружи
одинаковый ответ. В этом проекте такое уже случалось дважды — пустой буфер в
сверке видеопамяти и выброшенный компилятором код в замере вычислений. Отсюда
общее правило: **если проверка не доказала, что умеет находить ошибки, её
«ошибок нет» ничего не значит.**

### Нагрузка видеокарты: свой вычислительный шейдер

`Core/Diagnostics/GpuStressWorker.cs`. Владелец выбрал полноценную нагрузку
(из вариантов «пакет Vortice / чистый P/Invoke / только наблюдать»).

Это **обычное использование графического API на собственном устройстве**: свой
`ID3D11Device`, свой шейдер, свои буферы. Хуков и внедрения в чужой процесс нет —
запрет правила 4 касается перехвата Present внутри процесса игры.

Шейдер делает две несвязанные вещи: греет (цепочки FMA над `float4` плюс чтение
и запись большого буфера в видеопамяти по разбросанным адресам) и проверяет
правильность (отдельная целочисленная часть, сверяется с эталоном на CPU).
**Разделение принципиальное:** сверять float-вычисления нельзя, компилятор
шейдеров вправе переупорядочить операции.

**Три вещи, найденные замером на живом прогоне у владельца:**

- **TDR.** Вызов дольше двух секунд — и Windows считает драйвер зависшим.
  Объём работы подбирается калибровкой под ~25 мс.
- **Эталон дороже нагрузки.** Первая версия разгонялась до 4 000 000 итераций,
  и «вызов видеокарты» занимал 4,5 секунды — это было время ПРОЦЕССОРА,
  считавшего эталон в один поток. Лечится потолком итераций и разовым расчётом
  эталона при фиксированном зерне.
- **`CopyResource` молча не копирует ничего при разных размерах ресурсов.**
  Приёмник был 4 КБ против 4 МБ источника «ради экономии шины» — в staging
  оставались нули, сверка не совпадала никогда, и на исправной карте счётчик
  дорос до 8 916 320 256 «ошибок». Диагностировано по кратности 1024 (все
  проверяемые значения каждый раз) при чистых `nvidia-smi` и журнале Windows.

**Первая версия грела вдвое слабее возможного** — владелец заметил сам по
температуре. Замер подтвердил: 121 Вт из 250 Вт лимита, 57 °C. Причины: шейдер
крутил целочисленный хеш в регистрах, видеопамять не трогал вовсе, и
синхронизация на каждом вызове оставляла карту простаивать, пока процессор
забирал результат. Отсюда переписывание под FMA + видеопамять + пакет из восьми
вызовов на одну синхронизацию. **Счётчик «загрузка GPU» в такой ситуации
бесполезен: он показывает «был ли занят хоть один блок», а не насколько** —
при 121 Вт он честно рисовал 97%.

### Отчёт о сбоях: четыре источника, ни один не полон

`Core/Diagnostics/CrashReportTest.cs` собирает картину из журналов Windows,
файлов дампов, собственного чёрного ящика и настроек записи дампа. Коды синего
экрана расшифровывает `BugCheckCodes.cs`; незнакомый код показывается как есть,
с честной пометкой «расшифровки нет».

Журналы читаются через `EventLogReader` с XPath-фильтром, а не запуском
`Get-WinEvent`: внешний процесс стоил бы 150–300 мс на каждый из десятка запросов.

**Фильтр по уровню события обязателен.** Найдено на этой машине: `Ntfs` код 98 —
это информационное «Том D: работоспособен», и без фильтра `Level=1,2` отчёт
показывал двенадцать таких сообщений как «ошибки файловой системы».

`FormatDescription()` бросает исключение, когда манифест провайдера не
зарегистрирован (обычное дело для драйверов вроде `nvlddmkm`): текст события
пуст, и смысл несут только именованные поля `EventData` из XML.

### Вкладка «Стресс-тест» с живыми графиками

Отдельная вкладка, а не кнопка среди разовых тестов: стресс-тест идёт часами, и
смысл в динамике. Ступенька на графике скорости ровно тогда, когда температура
упёрлась в потолок, — это троттлинг, увиденный глазами; в текстовом итоге он
превращается в строчку «падение 12%», по которой не понять ни когда, ни почему.

Числа для графиков идут отдельным каналом `IProgress<StressTick>` раз в секунду,
рядом с текстовым `IProgress<TestLine>` (строки — раз в 15 секунд).

**Подписи нижней оси скрыты намеренно:** у `DataStreamer` координата X — номер
слота в кольцевом буфере, на экране это выглядит как «−11 … 11». Время показывают
счётчики «Прошло/Осталось». У оси загрузки пределы зафиксированы 0…105 и
`ManageAxisLimits = false`, иначе автомасштаб превращает ровные 100% в шумную
ленту около единственного значения.

## Диагностика видеокарты: паспорт, память, замеры (2026-09-13)

Владелец попросил полноценную проверку видеокарты — «и для игр, и для LLM» —
потому что карта куплена с рук и немолодая (RTX 2080 SUPER, Turing, 2019).

### Паспорт — три источника, ни один не полон

`Probes/GpuInfoProbe.cs`: DXGI даёт производителя, идентификаторы и объём памяти;
Direct3D 11 — что карта умеет (уровень, половинная и двойная точность);
`nvidia-smi` — то, чего в DirectX нет вовсе: VBIOS, вычислительные возможности,
состояние шины PCI Express и пределы мощности. Для карты с рук последнее самое
интересное: по нему видно и вмешательство в прошивку, и работу на урезанной шине
(типичный след райзера после майнинга).

**Грабля: `(long)desc.DedicatedVideoMemory` переполняется.** У Vortice это
`PointerUSize`, и прямое приведение к `long` идёт через неявный оператор в `uint`.
На любой карте от четырёх гигабайт это `OverflowException`, и весь сбор паспорта
возвращал «видеокарта не определилась». Приводить только через `(long)(ulong)`.

### Проверка видеопамяти — MemTest для видеокарты

`Diagnostics/GpuMemoryTest.cs`. Занимает почти всю свободную видеопамять блоками
по 256 МБ, пишет шаблоны (нули, единицы, две шахматные, адресный, псевдослучайный)
и сверяет обратно. **Сверка идёт на самой видеокарте** — шейдер сравнивает и
считает несовпадения атомарным счётчиком: тащить гигабайты через шину ради
сравнения было бы в сотни раз медленнее.

**Самопроверка обязательна.** Тест сначала заведомо ломает сверку (пишет нули,
проверяет единицами) и убеждается, что счётчик сработал. Без этого неработающий
тест выглядел бы точно так же, как исправная память, — и это худший вид неверного
результата. Урок взят из истории с `CopyResource` ниже.

### Замеры: память, вычисления, шина

`Diagnostics/GpuBenchmark.cs`. Синхронизация через `ID3D11Query` типа Event —
иначе замерялось бы время постановки команд в очередь.

**Грабля, которую ловит только здравый смысл:** первая версия показывала
40 TFLOPS у карты, у которой по паспорту 11,2. Компилятор шейдеров увидел, что
три вычислительные цепочки из четырёх почти не влияют на результат (он писался
под условием «если равно 1e30»), и выбросил их. Лечится безусловной записью
результата. **Правило: если замер показал больше паспортных значений — это
ошибка замера, а не удачная карта.** После правки — 11,4 TFLOPS, то есть 101%.

### Нейросети: FP16 через Direct3D 11, DirectML не заработал

`Diagnostics/GpuLlmBenchmark.cs` меряет вычисления половинной точности через
`min16float` в обычном вычислительном шейдере. На RTX 2080 SUPER даёт 19,6 TFLOPS
против 10,8 у одинарной — ×1,8, ровно как и ожидается от FP16 на обычных блоках.

**Тензорные блоки этим не измеряются, и это честно сказано в выводе.** Штатный
путь к ним — DirectML; он был реализован (D3D12 + `GeneralMatrixMultiplyOperator`,
пакеты `Vortice.DirectML` и `Vortice.Direct3D12` остались в проекте), но не
заработал: умножение давало нули при корректно записанных входных данных, а
попытка обойти это пересозданием таблицы привязок приводила к
`DXGI_ERROR_DEVICE_REMOVED`. Отладочный слой Direct3D 12 на этой машине
недоступен (не установлен компонент «Средства графики»), поэтому причина не
найдена. Работа остановлена сознательно: каждый сброс устройства — риск для
подозрительной карты, а мерить всё равно есть чем. Подробности — в `tasks.md`.

**Проверка результата важнее самой цифры.** Замер DirectML показывал
1342 TFLOPS — при том, что умножение не выполнялось вовсе. Поймано сверкой:
входы заполняются единицами, значит каждый элемент произведения обязан равняться
числу столбцов. Без этой проверки в отчёт ушли бы фантастические числа.

### Выводы для владельца

`Diagnostics/GpuDiagnosticTest.cs` сводит всё вместе и отвечает на два вопроса:
что карта даёт в играх (класс разрешения по вычислительной мощности, достаточность
видеопамяти) и что она даёт языковым моделям (какой размер модели влезает в
каждом формате квантования и каков предел скорости выдачи слов).

Оценка скорости LLM опирается на физику, а не на таблицы: чтобы выдать одно
слово, модель читает все свои веса, поэтому предел равен пропускной способности
памяти, делённой на размер модели. На практике выходит примерно вдвое меньше —
это в выводе сказано прямо.

## Права администратора без UAC-запроса (2026-09-13)

Владелец: «Сделай, чтобы приложение работало из коробки. Надоедает постоянно
переключать на админские права».

Половина возможностей требует администратора: температуры (драйвер чтения
датчиков), счётчик кадров (сеанс ETW), очистка списка ожидания памяти. Три
способа получить права, и два плохи:

- **манифест `requireAdministrator`** — UAC-окно при каждом запуске, включая
  автозапуск вместе с Windows. Для программы, которая работает постоянно, — нет;
- **перезапуск через `runas`** — то же окно, только вручную;
- **задача в Планировщике с уровнем «Наивысшие права»** — Windows поднимает
  процесс как системная служба, минуя обычный путь элевации через проводник, и
  потому без диалога. Подтверждение нужно ровно один раз: при создании задачи.

Выбран третий (`App/ElevationService.cs`). Манифест остался `asInvoker` —
портативной копии на чужой машине права могут быть не нужны вовсе.

**Как это работает при запуске.** `App.OnStartup` до создания окна проверяет:
прав нет, автоповышение включено, задача существует и указывает на этот же exe —
значит перезапускаемся через `schtasks /Run` и завершаемся. Пользователь видит
обычный запуск, просто уже с правами.

Три вещи, без которых это не работает:

- **Mutex единственного экземпляра нужно отпустить до перезапуска.** Иначе новый
  процесс увидит «уже запущено» и тихо выйдет, а старый к тому моменту закроется.
  Отсюда `SingleInstance.ReleaseForRelaunch()`;
- **Защита от зацикливания.** Задача запускает exe без аргументов, поэтому
  поднятый ею экземпляр не может узнать о перезапуске из командной строки. Если
  задача почему-то не даёт прав (сломана, запрещена политикой), приложение
  перезапускало бы себя бесконечно. Метка на диске с временем последней попытки
  разрывает круг;
- **`StandardOutputEncoding` у `schtasks` задавать нельзя.** Попытка читать вывод
  как Unicode превращает XML в иероглифы, `<Command>` не находится, задача
  считается ненастроенной — и автоповышение молча не срабатывает. Поймано
  живым запуском: процесс оставался с обычными правами, а следов в логах не было.

Состояние задачи кэшируется на десять секунд: окно настроек спрашивает его
трижды подряд (состояние, описание, доступность кнопок), а каждый ответ — это
запуск внешнего процесса.

## Тензорные блоки видеокарты через DirectML (2026-09-13)

`Core/Diagnostics/GpuTensorBenchmark.cs`. Измеряет умножение матриц — операцию,
из которой состоит работа языковой модели, — на тензорных блоках.

Путь оказался долгим, и цена ошибки здесь выше обычного: неверные вызовы DirectML
не дают исключения, а роняют устройство Direct3D 12 целиком.

**Ошибка была одна, и она в документации.** У оператора `DML_OPERATOR_GEMM` три
входа: A, B и необязательное слагаемое C. Привязать нужно **все три**, для
неиспользуемого — пустую привязку `DML_BINDING_TYPE_NONE`. Документация
`IDMLBindingTable::BindInputs` обещает за неполный набор именно удаление
устройства. Отсюда обе загадки разом: молчаливые нули в результате (устройство
уже мертво, а исключение ещё не брошено) и `DXGI_ERROR_DEVICE_REMOVED` при
следующем обращении.

**Обёртка Vortice 3.8.3 пустую привязку не умеет** — `default(BindingDescription)`
падает с `NullReferenceException`, исправление вышло уже после релиза. Обходной
путь через фиктивный тензор C из одного значения работает, но мешает DirectML
выбрать быструю реализацию: с ним замер давал 6,5 TFLOPS вместо 50. Поэтому
входы привязываются прямым вызовом через таблицу виртуальных методов COM-объекта
(`BindInputsRaw`), где пустую привязку можно выразить честно. Номер метода (8)
взят из заголовка `DirectML.h`.

Остальное, что обязательно и не очевидно:

- `SetDescriptorHeaps` вызывается **после каждого** `CommandList.Reset()` —
  список команд забывает привязанные кучи дескрипторов;
- у инициализатора оператора входы не привязываются вовсе (тензоров, которыми
  владеет DirectML, нет), а постоянный ресурс привязывается как его **выход**;
- буферы создаются в состоянии `Common`, на время заливки переводятся в
  `CopyDest`, дальше живут в `UnorderedAccess` — Direct3D 12 состояния не
  угадывает;
- `GC.KeepAlive` на таблицу, кучу и ресурсы: таблица привязок не держит на них
  сильных ссылок, и финализатор обёртки мог бы освободить их под работающим GPU;
- `DeviceRemovedReason` проверяется в цикле ожидания. Удаление устройства
  «липкое»: дальше всё возвращает ошибку, и без ранней проверки причина теряется
  за вторичными симптомами.

**Результат на RTX 2080 SUPER: 58,6 TFLOPS в половинной точности против 9,9 в
одинарной — ускорение в шесть раз, 103% от паспортной пиковой цифры.** Для
сравнения, тот же замер обычным вычислительным шейдером (`GpuLlmBenchmark`,
остался запасным путём) даёт 19,6 TFLOPS: тензорные блоки из шейдера недоступны.

Матрица 2048×2048 и пакет из восьми умножений на один список команд подобраны
опытом: на 1024 и по одному умножению замер показывал 4,4 TFLOPS в обеих
точностях — мерились накладные расходы, а не видеокарта.

## Игровой замер видеокарты (2026-09-13)

`Core/Diagnostics/GpuGameBenchmark.cs`. Вычислительный шейдер нагружает только
математику; в игре работают ещё растеризатор, блоки выборки текстур и кэши — и
узким местом часто оказываются именно они. Поэтому кадры рисуются по-настоящему:
полноэкранный треугольник, тяжёлый пиксельный шейдер с шумом, освещением и
выборкой из текстуры.

Кадр идёт в собственную текстуру, а не в окно: окно потребовало бы синхронизации
с монитором, и замер упёрся бы в частоту обновления экрана.

Кроме среднего числа кадров считается «худший процент» — именно редкие долгие
кадры ощущаются как рывки, и по среднему их не видно. Отношение одного к другому
показывается как «ровность кадров».

Сложность шейдера подобрана так, чтобы результат попадал в привычный игровой
диапазон: на RTX 2080 SUPER — 98 кадров при ровности 95%. При меньшей сложности
карта выдавала 548 кадров в секунду, и число переставало что-либо значить на глаз.

## Окно видимой нагрузки: картинка и FPS (2026-09-14)

`Core/Diagnostics/GpuVisualLoad.cs` + `App/GpuLoadWindow.xaml(.cs)`. То же, что
делает FurMark своим мохнатым бубликом. Картинка ничего не измеряет — карта
греется от расчёта кадра, вывод на экран стоит доли процента; смысл в том, что
нагрузку видно и видно, ровно ли ложатся кадры.

Сцена — тор с «мехом», считается трассировкой лучей в одном пиксельном шейдере:
геометрии нет, есть формула расстояния до поверхности, и для каждого пикселя луч
шагает к ней. Мех — пять слоёв шума разного масштаба, каждый считается на каждом
шаге луча и трижды повторно при взятии нормали.

**Direct3D рисует в собственное дочернее окно Win32** (`HwndHost` класса "static"),
а не в поверхность WPF. WPF рисует через ту же видеокарту, и деление одной
поверхности кончается миганием и потерей кадров. Отдельное окно разводит их
полностью: сверху обычные подписи WPF, внутри чистый Direct3D.

**Четыре грабли, каждая превращала нагрузку в заставку или в ложь:**

1. **Без `AllowTearing` композитор Windows держит частоту монитора.** `Present(0, …)`
   сам по себе не помогает: на 144-герцевом экране выходило ровно 144 кадра и 26%
   загрузки. Флаг нужен и в `SwapChainDescription1.Flags`, и в `Present`. Картинка
   при этом может рваться по горизонтали — для теста это признак, что ограничения
   сняты, а не порок.

2. **Нагрузка не должна зависеть от размера окна.** Сцена считается в постоянном
   разрешении и только потом растягивается в окно вторым проходом. Иначе в
   маленьком окне пикселей вчетверо меньше, и карта недогружена.

3. **Регулятор нагрузки — количество пикселей, а не шагов луча.** Рост потолка
   шагов с 220 до 420 не изменил время кадра вовсе: лучи заканчиваются, коснувшись
   поверхности или уйдя за сцену, и до потолка не доходят. Замерено: 2560×1440 —
   80% и 177 Вт, 3840×2160 — 94–96% и 204–217 Вт из 250.

4. **Счётчик Windows «GPU Engine» занижает загрузку.** Он меряет долю времени, что
   планировщик WDDM держал на движке пакеты конкретного процесса. Замерено под
   полной нагрузкой: счётчик 58%, сама карта 93% при 200 Вт — разница в тридцать
   пять пунктов. Для окна, которое существует ровно затем, чтобы показать
   настоящую занятость карты, это недопустимо. Введён `Probes/NvidiaLiveProbe.cs`:
   один долгоживущий процесс `nvidia-smi -l 1`, который сам печатает строку раз в
   секунду. Запускать nvidia-smi заново на каждый опрос нельзя — старт стоит около
   сотни миллисекунд и создаёт всплеск нагрузки посреди замера. Побочная выгода:
   температура читается **без прав администратора**, в отличие от датчиков через
   `LibreHardwareMonitorLib`.

**Форма фигуры — отдельная работа, а не украшение.** Свободное вращение по двум
осям регулярно поворачивало бублик ребром к зрителю, кольцо толщиной 0.38
затягивало дырку, а крупный шум съедал силуэт — на экране был бесформенный
камень. Рабочее сочетание: постоянный наклон 0.95 рад, вращение только вокруг
собственной оси, кольцо 0.26, амплитуды шума от 0.030 до 0.002.

**Гипотеза, которая не подтвердилась.** Худший процент держится втрое ниже
среднего (45 против 106). Ограничение глубины очереди кадров
(`IDXGIDevice1.MaximumFrameLatency = 1`) не изменило его вовсе — причина не в
очереди. Настройка оставлена: с ней замеренное время кадра относится к тому
кадру, который сейчас на экране. Остаётся версия про единичные заминки
композитора Windows, для проверки нужен разбор ETW по событиям DWM.

Защита: автоостановка при 90 °C, упрощение сцены, если кадр дольше 200 мс (порог
перезапуска видеодрайвера — 2 секунды).

## Шлюз при поднятом VPN (2026-09-13)

`NetworkUtils.GetDefaultGateway()` брал первый попавшийся шлюз из списка
адаптеров. При активном VPN (WireGuard/AmneziaVPN) туннельный адаптер объявляет
своим шлюзом `0.0.0.0` — пробы уходили в несуществующий адрес, и график «шлюз»
показывал ровные **100% потерь на полностью исправной сети**. Обнаружено по
собственному чёрному ящику в первый же его запуск.

Исправлено двумя шагами: сначала выбрасываются адреса, до которых пинговать
бессмысленно (`0.0.0.0`, loopback, APIPA `169.254.x`, multicast), затем
оставшиеся ранжируются — физический адаптер впереди туннеля и виртуального.
Виртуальные определяются **по названию драйвера**, а не по типу интерфейса:
WireGuard, TAP и Hyper-V представляются системе обычными сетевыми картами.
Этим же закрыт давний технический долг про Hyper-V/WSL. Проверено живьём:
до правки 100% потерь, после — 0,94–2,76 мс и 0% потерь до настоящего роутера.

## Осиротевший драйвер WinRing0 блокировал удаление Program Files (2026-08-25)

Владелец не смог удалить `C:\Program Files\NetAudit` — в папке остался единственный
файл `NetAudit.App.sys`, 14 КБ. Это не мусор от прерванной установки: `driverquery`
показал реально загруженный в ядро драйвер `R0NetAudit_App` (WinRing0, его подгружает
`LibreHardwareMonitorLib` для доступа к MSR/SMBus при чтении температуры — тот же
класс требования прав администратора, что у ETW-сеанса FPS). Пока драйвер загружен,
Windows держит файл открытым точно так же, как открытую библиотеку внутри живого
процесса — обычное «файл используется другой программой», просто без окна с этой
фразой, потому что удаление шло из elevated-сессии без Explorer.

`TemperatureProbe.Dispose()` в коде вызывает `_computer.Close()` и выгружает драйвер
корректно — но только при штатном закрытии программы. `Stop-Process -Force`
(что делает `pre-uninstall.ps1`, и что несколько раз в этой сессии делал агент
при тестах) сигнализирует процессу на завершение напрямую, минуя `Dispose()` —
драйвер остаётся висеть в ядре до перезагрузки Windows, независимо от того, жив ли
породивший его процесс. **Установщик этот файл не убирал не по недосмотру, а
принципиально**: `[Files]` в `NetAudit.iss` копирует только то, что перечислено
(содержимое `dist\NetAudit-vX.Y.Z\`), а `NetAudit.App.sys` — не файл сборки, его
runtime создаёт сама библиотека при первом запуске от администратора. Inno Setup
не синхронизирует папку и не трёт файлы, которых нет в его собственном манифесте —
ни при установке, ни (для файлов, не установленных им самим) при удалении.

`Get-Service`/`Stop-Service` этот драйвер в этой конфигурации не видят вообще
(вернули пусто), только `driverquery`/`sc.exe` — драйверный тип службы (Type=1,
SERVICE_KERNEL_DRIVER), а не обычная Win32-служба, `Get-Service` их не всегда
перечисляет.

**Исправлено**: `pre-uninstall.ps1` после остановки процесса гасит и удаляет
`R0NetAudit_App` через `sc.exe stop`/`sc.exe delete` — теперь удаление и обновление
через установщик не оставляют этот файл, даже если процесс перед этим убивали
принудительно. Ручной сиюминутный фикс для уже осиротевшего файла — те же две
команды `sc.exe`, потом `Remove-Item` папки.

## Диагностика оперативной памяти (2026-09-14)

`Core/Probes/RamInfo.cs` + `RamInfoProbe.cs`, `Core/Diagnostics/RamDiagnosticTest.cs`
+ `RamBenchmark.cs` + `RamIntegrityTest.cs`. Устроено по образцу диагностики
видеокарты: паспорт → состояние → следы сбоев → замеры → проверка → выводы.

### Паспорт: сырые таблицы SMBIOS вместо WMI

`GetSystemFirmwareTable('RSMB')` и свой разбор записей типа 16 (подсистема
памяти) и 17 (модуль). WMI (`Win32_PhysicalMemory`) читает те же таблицы, но
теряет по дороге **число рангов, диапазон напряжений и тип коррекции ошибок** —
а ранги и напряжение как раз и нужны, чтобы судить о настройке. Прав
администратора разбор не требует, внешних процессов не запускает. WMI остался
запасным путём на случай виртуальной машины с урезанным BIOS.

Грабли разбора, каждая ловится только на реальной таблице:
- размер модуля в поле 0x0C — в мегабайтах, но при значении `0x7FFF` настоящий
  размер лежит в расширенном поле 0x1C, а бит 15 переключает единицу на килобайты;
- строки записи нумеруются **с единицы** и лежат сразу за структурной частью,
  весь блок заканчивается двумя нулями подряд;
- производителя BIOS часто пишет как `Unknown` — такое лучше не показывать вовсе,
  чем показывать «Unknown BLS8G4D32AESCK».

**Таймингов (CL-tRCD-tRP-tRAS) в SMBIOS нет и быть не может** — они лежат в
микросхеме SPD на самой планке и читаются по шине SMBus, то есть драйвером уровня
ядра. Косвенная замена — измеренная задержка случайного доступа.

### Включён ли XMP — прямого ответа не существует

SMBIOS сообщает только текущую скорость. Профиль определяется по трём косвенным
признакам: паспортная скорость модуля выше рабочей, рабочая частота совпадает с
одной из штатных частот JEDEC, напряжение 1,2 В у DDR4 (профили разгона просят 1,35).
В отчёте это так и называется — «скорее всего выключен», без выдумывания
уверенности, которой нет.

### Замеры

Многопоточные (`Parallel.For`, потоков по числу логических ядер): одно ядро
физически не выбирает всю полосу двухканального контроллера — на этой машине
15 ГБ/с одним ядром против 23 ГБ/с всеми. Однопоточное чтение меряется отдельно
как самостоятельная величина.

- **Запись — потоковая, мимо кэша** (`Avx.StoreAlignedNonTemporal` + `Sse.StoreFence`).
  Обычная запись сначала читает строку кэша, чтобы изменить её часть, и замер
  показывал бы смесь чтения с записью. Барьер обязателен: потоковые записи оседают
  в отдельном буфере процессора и без него часть не дошла бы до памяти к остановке
  секундомера.
- **Буферы адресуются через `nint`, а не через `byte*`.** Указатель нельзя
  захватить в лямбду, а работа потокам раздаётся именно лямбдой — компилятор
  отвергает захват, и `a + off` требует явного `(nint)off`.
- **Задержка — обход перемешанной цепочки индексов**: адрес следующего шага
  известен только после чтения текущего, поэтому предзагрузка процессора
  бессильна. Та же цепочка на семи размерах области даёт лесенку, по которой
  видно кэши: на Ryzen 5 2600 — 1,6 нс (L1), 4,2 (L2), 10–37 (L3), дальше 85–118 нс ОЗУ.

Уровень кэша в отчёте определяется по абсолютной задержке, а не по скачку
относительно предыдущей строки: пороговый скачок помечал «вышли за кэш» почти
на каждой строке лесенки, потому что задержка растёт плавно.

### Проверка шаблонами

Семь шаблонов (нули, единицы, две шахматки, бегущая единица, собственный адрес
ячейки, псевдослучайный). Весь объём сначала записывается целиком и только потом
сверяется — между записью и чтением данные успевают покинуть кэш, иначе
сверялся бы кэш, а не планки.

Занимается не более 60% свободной памяти и не ближе 1,5 ГБ к её концу: если
занять всё, Windows начнёт выгружать наши же страницы в файл подкачки, и тест
будет проверять диск. Из-под работающей системы полная проверка невозможна в
принципе — область ядра и драйверов недоступна; в отчёте это сказано прямо,
с отсылкой к загрузочному MemTest86.

### Переносимость на чужие машины (проверено разбором, 2026-09-14)

Владелец спросил, подойдёт ли это всем ПК — вопрос вскрыл четыре места, где код
на другом железе соврал бы.

**1. Числу слотов из BIOS верить нельзя.** На Gigabyte B450M S2H SMBIOS сообщает
**четыре** слота и потолок 128 ГБ, а физически на плате их **два** и потолок 32 ГБ:
прошивка описывает возможности контроллера памяти процессора, а не разведённое
на плате. Записи Type 17 это не спасают — их тоже четыре (DIMM 0 и DIMM 1 в каждом
канале, две пустые). Надёжного способа узнать физическое число слотов из системы
нет вовсе. Поэтому отчёт печатает «Слотов, по данным BIOS», перечисляет названные
пустыми слоты и прямо предупреждает сверяться со спецификацией платы, а совет по
расширению даётся в двух вариантах — «если слоты свободны» и «если все заняты».
Первая версия отчёта на этой машине советовала докупить две планки, которые
некуда ставить.

**2. Каналы вычитываются из названия банка, а называет их BIOS как хочет.** Пустой
результат раньше молча превращался в «один канал» → теоретический предел вдвое
занижался → «достигнуто 120% от предела». Теперь `RamInfo.ChannelsKnown` отделяет
«каналов один» от «каналы не разобраны», `TheoreticalGbs` в последнем случае равен
нулю, и блок про эффективность просто не печатается.

**3. Буфер замера должен превышать кэш последнего уровня.** 32 МБ минимума
целиком помещаются в кэш AMD X3D (96 МБ) или серверного процессора — «скорость
памяти» вышла бы кратно завышенной. Размер кэша берётся через
`GetLogicalProcessorInformation` (разбор по сырым байтам: запись 32 байта, тип
связи по смещению 8, размер кэша по 20), буфер запрашивается вчетверо больше;
если свободной памяти не хватило — в отчёте предупреждение, что цифра завышена.

**4. Нумерация форм-фактора у SMBIOS и WMI сдвинута на единицу** (DIMM — это 9 в
SMBIOS и 8 в WMI). Общая таблица на оба источника тихо превращала DIMM в TSOP, а
SODIMM в RIMM. Разведено на два метода. Коды типа памяти (DDR4 = 0x1A), наоборот,
у обоих источников общие — там таблица одна.

Остальное переносится без оговорок: разбор SMBIOS не требует прав администратора
и работает на любой Windows с UEFI/BIOS (в виртуальной машине таблицы могут быть
пустыми — тогда включается запасной путь через WMI); векторные пути замера
включаются по `Avx.IsSupported`/`Avx2.IsSupported`, без них считается скалярно и
в отчёт добавляется строка о заниженном результате; счётчики памяти берутся из
WMI-класса, а не из локализованных имён `PerformanceCounter`. Непроверенным
остаётся DDR5, SODIMM, одноканальные и разнородные конфигурации — см. `tasks.md`.

### Замеренное на машине владельца (Ryzen 5 2600, B450M S2H, 2×8 ГБ DDR4)

Комплект Crucial Ballistix `BLS8G4D32AESCK` (паспортные 3200). До 2026-09-14
работал на 2400 МТ/с — профиль XMP в BIOS не был включён, это и нашла
диагностика. Двухканальный режим, одноранговые модули. BIOS сообщает 4 слота,
на плате их 2 — оба заняты.

| Что | На 2400 (было) | На 3200 (стало) |
|---|---|---|
| Чтение | 22,6–24,2 ГБ/с | 33–38 ГБ/с |
| Запись | 19,6–20,1 ГБ/с | 28,5–31 ГБ/с |
| Копирование | 11,2 ГБ/с | 16,3 ГБ/с |
| Чтение одним ядром | 14,7–15,1 ГБ/с | 16,1–21,9 ГБ/с |
| Задержка | 107–118 нс | 88,7–91,4 нс |
| Достигнуто от предела | 59–62% (из 38,4) | 74% (из 51,2) |

**Профиль XMP включён владельцем 2026-09-14** (M.I.T. → Advanced Frequency
Settings → Extreme Memory Profile → Profile1). Прирост подтверждён замерами,
проверка шаблонами на новой частоте ошибок не нашла, журнал после перезагрузки
чист. Разброс цифр между прогонами — от фоновой нагрузки: тот же замер на
занятой машине даёт на четверть меньше, чем на свободной.

Две вещи, которые вылезли после включения профиля и потребовали правок:

- **BIOS не переписывает напряжение в таблицах SMBIOS.** Частота стала 3200, а
  в поле напряжения по-прежнему штатные 1,20 В вместо профильных 1,35. Отчёт
  теперь предупреждает об этом, иначе выглядит так, будто профиль применился
  наполовину.
- **Задержку нельзя трактовать в отрыве от частоты.** Текст «так выглядит память
  без профиля XMP» печатался при 91 нс — уже с включённым профилем. У Ryzen до
  Zen 3 дорога до планок идёт через внутреннюю шину, и 85–95 нс там нормальны.
  `RamBenchmark` получил необязательный паспорт памяти и при высокой частоте
  говорит про архитектуру процессора, а не про выключенный профиль.

Занято 11–12 ГБ из 16, обещано программам 107–110% от объёма планок, около
1 ГБ памяти Windows держит в сжатом виде. Синих экранов по памяти и ошибок
WHEA за 60 суток нет, проверка шаблонами ошибок не нашла.


## Диагностика процессора (2026-09-14)

`Core/Probes/CpuInfo.cs` + `CpuInfoProbe.cs` + `CpuAffinity.cs`,
`Core/Diagnostics/CpuDiagnosticTest.cs` + `CpuBenchmark.cs` + `CoreLatencyTest.cs`.
Устройство то же, что у диагностик видеокарты и памяти: паспорт → состояние →
следы сбоев → замеры → выводы.

### Счётчикам частоты Windows верить нельзя

Главное открытие этой работы. `Win32_PerfFormattedData_Counters_ProcessorInformation`
на AMD показывает **политику питания, а не факт**: под нагрузкой одного потока все
двенадцать логических процессоров одинаково отдавали `PercentProcessorPerformance =
110`, включая простаивающие. «Частота на одном ядре» выходила равной частоте на
всех — то есть замер был бесполезен.

Частота меряется своим способом: **цепочка зависимых 64-битных умножений**. У
`imul` задержка ровно три такта на всех x86 последних поколений, следующее
умножение не может начаться раньше — сколько их уложилось в секунду, столько было
тактов. Сверено двумя независимыми способами: цепочка сложений дала 3,55 ГГц,
умножения 3,67 ГГц, а замер FMA (59,2 GFLOPS при 16 операциях за такт) — 3,70 ГГц.
Расхождение в пределах трёх процентов, и эта цифра честно названа в отчёте.

Три вещи, каждая стоила отдельного прогона:

- **Цикл нельзя разворачивать.** Восемь умножений на одну константу подряд
  компилятор сворачивает в одно, и замер показал 29 ГГц. Одно умножение на виток
  цикла свернуть невозможно.
- **Нулевое ядро систематически медленнее.** Разброс по ядрам доходит до 13%
  (3,25 ГГц на нулевом против 3,68 на лучшем): на нулевом Windows обрабатывает
  прерывания, а у AMD часть ядер отмечена как предпочтительные и поднимается выше.
  Поэтому «частота одного ядра» — это максимум по ядрам, а не замер на нулевом.
- **Порядок замеров решает.** Частоту одного ядра надо мерить **до** тяжёлых фаз:
  после них тот же замер давал на 8% меньше, и разница с all-core пропадала.
  Сейчас порядок такой: частота лучшего ядра → целые числа → частота всех ядер
  (на прогретом процессоре, что и есть честная устойчивая частота).

Потоки замера привязываются к ядрам **через один** (`CpuAffinity.Pin`): логические
процессоры 0 и 1 живут на одном физическом ядре и делят блоки исполнения — посадить
на оба значит получить вдвое заниженную частоту.

### Задержки между ядрами

`CoreLatencyTest` меряет пинг-понг между каждой парой логических процессоров и
раскладывает результат по трём корзинам: потоки одного ядра, ядра одного кластера,
разные кластеры. На Ryzen 5 2600 это сразу показывает устройство: 34–35 нс внутри
кластера против 90–160 нс между кластерами, то есть в 1,8 раза дороже.

Шум здесь односторонний — прерывание может обмен только задержать. Поэтому берётся
**лучший результат из трёх подходов**, а в сводках — **медиана, а не среднее**: без
этого одна пара с прерыванием (105 нс там, где у соседних пар 25–28) сдвигала
среднее и делала сводку бессмысленной.

### Паспорт

Кэши читаются старым `GetLogicalProcessorInformation` (запись фиксированные 32
байта), раскладка ядер — расширенным `GetLogicalProcessorInformationEx` с
`RelationProcessorCore`: только он сообщает класс энергоэффективности, по которому
различаются P- и E-ядра гибридных процессоров Intel. Смещения внутри описания ядра
между версиями Windows не менялись, а вот у описания кэша менялись — отсюда разные
функции для разных задач.

Кэш последнего уровня, разбитый на несколько блоков, — это кластеры ядер. На
Ryzen 5 2600 их два по 8 МБ: суммарные «16 МБ L3» из характеристик одному ядру
недоступны, и отчёт говорит об этом прямо.

Поколение определяется по семейству и модели (Family 23 Model 8 = Zen+). Таблица
неполная намеренно: неизвестное сочетание отдаёт пустую строку, и поколение просто
не показывается — это честнее, чем назвать процессор чужим именем.

| Что | Значение |
|---|---|
| Целые числа, одно ядро / все | 596 / 5826 млн оп/с (×9,8 из ×12, отдача 81%) |
| Плавающая точка FMA | 59,2 / 334 GFLOPS |
| Шифрование AES | 48–52 ГБ/с |

## Слой интерфейса после аудита (2026-09-14)

Правки в `NetAudit.App/`, вызванные внешним аудитом. Три решения стоит помнить.

**Списки в настройках нельзя считать заполненными.** Значения по умолчанию у
`List<string>` задаются при объявлении, но `System.Text.Json` их перетирает:
строка `"GameModeExcludedProcesses": null` в файле кладёт в поле именно `null`.
`SetupGameBoost` вызывается из конструктора `MainWindow` вне `try`, поэтому
`foreach` по такому списку ронял программу до появления окна — снаружи это
выглядело как «не запускается вообще». `AppSettings.Load` теперь прогоняет
`EnsureLists`, а `CopyFrom` копирует списки через `??`.

**Подстановка в одинарные кавычки PowerShell требует удвоения апострофа.**
`New-ScheduledTaskAction -Execute '{exe}'` рвался на пути вида
`C:\Users\O'Brien\...`: задача не создавалась никогда, а сообщение об ошибке было
невнятным. Это же закрывало и подстановку произвольного кода через имя папки.
Правило общее: любой путь и любое имя, попадающее в скрипт, идёт через
`.Replace("'", "''")`.

**Границы экрана считаются от виртуального экрана, а не от основного монитора.**
`SystemParameters.WorkArea` и `PrimaryScreenWidth` — это всегда основной монитор:
из-за них хоткеи углов швыряли оверлей с игрового экрана на основной, а открытие
окна настроек молча урезало сохранённую позицию. Для «того монитора, где окно
сейчас» берётся `System.Windows.Forms.Screen.FromHandle(hwnd).WorkingArea` —
WinForms отдаёт пиксели, поэтому границы переводятся в точки WPF через
`PresentationSource.FromVisual(...).CompositionTarget.TransformFromDevice`.
Общий помощник — `App.FitToScreen(Window)`: он же ужимает окна до рабочей области,
чтобы на экране 1366×768 и при масштабе 150% не уезжали нижние кнопки.

**Шлюз по умолчанию `192.168.1.1` убран.** В сетях 192.168.0.x и 10.0.0.x этот
адрес не отвечает никогда, и график показывал ровные 100% потерь — ложную аварию.
Теперь при неопределённом шлюзе подписка на его пробу просто не заводится, а
панель пишет «не определён». Полностью не создавать пробу нельзя без правки
`ProbeScheduler` в ядре — там шлюз обязателен.

**Порог остановки нагрузки на видеокарту — 97 °C.** Прежние 90 °C обрывали работу
сразу на картах, отдающих температуру горячей точки: у многих Radeon и у RTX 30 с
памятью GDDR6X 90–100 °C — рабочая норма. Какой датчик попадёт в показания,
решает модель карты, и текст остановки теперь об этом говорит.


## Аудит переносимости: что ломалось на чужом железе (2026-09-14)

Три субагента прочитали пробы, диагностики и интерфейс, ища допущения о
конкретной машине. Нашлось около восьмидесяти мест. Самое ценное — не список
правок, а классы ошибок, которые повторялись в разных файлах.

**Ноль вместо «неизвестно».** Самый частый и самый вредный класс. Счётчик не
ответил — «загрузка 0%». Прав не хватило — «защита виртуализации выключена».
Датчик не читается — «максимум температуры 0 °C». Раскладка ядер не опрошена —
«физических ядер столько же, сколько потоков», то есть «многопоточность
выключена» на обычном Ryzen. Везде, где источник может промолчать, теперь
хранится трёхзначное состояние, и отчёт говорит «узнать не удалось».

**Константа, снятая с этой машины.** Число итераций в замерах видеокарты
подбиралось под RTX 2080 SUPER: на встроенной графике тот же вызов длился
дольше двух секунд — порога, после которого Windows перезапускает видеодрайвер.
Буфер замера памяти в 96 МБ был «заведомо больше любого L3» ровно до появления
Ryzen с 3D-кэшем (96 МБ) и серверных процессоров (384 МБ). Пороги температур
80/90 °C объявляли перегретым исправный Ryzen 7000, у которого 95 °C — штатный
режим. Правило: любая константа, взятая из наблюдения за своим железом, обязана
стать либо замером, либо диапазоном.

**Разные тесты — разное железо.** Замеры звали `D3D11CreateDevice(null, …)`,
то есть адаптер по умолчанию, а тензорный замер выбирал карту с наибольшей
видеопамятью. На ноутбуке это две разные видеокарты, и в одном отчёте их цифры
стояли рядом. Появился `Diagnostics/GpuDeviceFactory.cs` — единственное место,
где выбирается адаптер.

**Внешние процессы и кодировки.** `netsh` пишет в кодовой странице консоли, а
`Encoding.Default` в .NET — это UTF-8: на русской системе разбор ломался, и
работающий Wi-Fi показывался отключённым. У `schtasks` та же беда с путями,
содержащими кириллицу. Перенаправленный stderr, который никто не читает, может
заблокировать процесс навсегда — так висел `nvidia-smi`.

**Апостроф в пути.** `-Execute '{exe}'` в скрипте PowerShell: путь вида
`C:\Users\O'Brien\…` обрывал строку, и задача в Планировщике не создавалась
никогда. Заодно это была возможность подставить чужой код через имя папки.

**Один экран.** Позиция оверлея, пределы ползунков и переброс по углам считались
от основного монитора. Настройки, перенесённые с двухмониторной машины, уносили
клик-сквозное окно за край экрана — вернуть его мышью нельзя по построению.

### Температуру процессора на этой машине прочитать нельзя

Не из-за прав: программа работает повышенно, а служба драйвера всё равно падает
с «Operation did not complete successfully because the file contains a virus or
potentially unwanted software». Библиотека `LibreHardwareMonitorLib` грузит
драйвер WinRing0, который Microsoft внесла в список уязвимых, а защита от них
включена (`HKLM\SYSTEM\CurrentControlSet\Control\CI\Config` →
`VulnerableDriverBlocklistEnable = 1`). Проверено по журналу System: события
7045 (служба установлена) и 7000 (сбой запуска) на каждый запуск программы.

`TemperatureProbe` теперь различает три случая — нет прав, драйвер заблокирован,
датчиков не нашлось — и говорит об этом прямо. Температура видеокарты не
страдает: её отдаёт сама карта через `nvidia-smi`.

Запасного пути для процессора нет: `MSAcpi_ThermalZoneTemperature` на этой плате
недоступен, `Win32_TemperatureProbe` пуст. Отключать защиту Windows ради
градусника не стоит, и в отчёте это сказано.


## Температуры видеокарты: ядро — не та цифра (2026-09-14)

У видеокарты не одна температура, а три, и различаются они сильно. На живой
RTX 2080 SUPER в покое: ядро 57 °C, горячая точка кристалла 68 °C, память 67 °C.
Под нагрузкой разрыв растёт.

**Ядро — самый холодный датчик**, и именно его отдаёт `nvidia-smi`
(`temperature.gpu`). Горячую точку и память он не отдаёт вовсе: на Turing поля
`Memory Current Temp` и `GPU T.Limit Temp` возвращают `N/A`. Зато их отдаёт NVAPI,
которым пользуется LibreHardwareMonitorLib — датчики называются «GPU Core»,
«GPU Hot Spot», «GPU Memory Junction».

Почему это важно, а не придирка: аварийная защита карты следит за ядром. Когда
перегревается память, ядро остаётся холодным, карта не сбрасывает частоты, а
просто зависает — чёрный экран, вентиляторы уходят в аварийные 100%, потому что
прошивка потеряла связь с управлением. В мониторинге при этом до последнего
спокойные цифры. Классический сценарий для карт, которым несколько лет не меняли
термопрокладки, и для тех, что пережили майнинг.

Поэтому: **для видеокарты берём максимум по датчикам, для процессора — сводный**
(`Package` у Intel, `Core (Tctl/Tdie)` у AMD). Раньше обе ветки шли через один
метод, который выходил по первому совпадению с «GPU Core», — до горячей точки
расчёт не доходил никогда.

Ориентиры: разрыв горячей точки с ядром под нагрузкой 10–15 °C у исправной карты,
больше 25 °C — высохшая термопаста. Память GDDR6 держит до 105 °C, после чего
карта сбрасывает частоты или виснет; 95 °C — рубеж для беспокойства.

### Датчики процессора и видеокарты живут раздельно

Процессору нужен драйвер ядра (WinRing0) и права администратора. Видеокарта
NVIDIA читается через NVAPI — **без прав вообще**, проверено запуском от обычного
пользователя. Раньше `TemperatureProbe.Initialize()` при отсутствии элевации
выходил сразу, и температуры карты не было ни в оверлее, ни в окне нагрузки, хотя
она была доступна. Теперь доступность считается раздельно: `CpuAvailable` и
`GpuAvailable`.

### Ноль — это не показание

Заблокированный драйвер не убирает датчик «Core (Tctl/Tdie)» из списка, а отдаёт
его со значением `0,0`. Проверка `sensor.Value is not null` такое пропускала, и
процессор показывался с температурой 0 °C. Годится только `> 0`: кремний холоднее
нуля не бывает. Тот же класс ошибок, что разбирался в аудите переносимости, —
«ноль вместо неизвестно», просто спрятанный на уровень глубже.


## Режим питания драйвера NVIDIA режет производительность молча (2026-09-14)

Карта под полной нагрузкой сидела на 1200 МГц из 2130 при 180 Вт из 250. Ни
троттлинга, ни лока частот, ни просадки 12 В; `nvidia-smi` называл причиной
`Idle` (маска 0x1) при загрузке 100%. Все замеры приложения при этом выглядели
правдоподобно — просто на треть ниже паспорта: 9 TFLOPS вместо 11, FurMark
90 FPS вместо 159.

Причина — «Режим управления электропитанием: Оптимальное энергопотребление»
в панели NVIDIA. Это умолчание драйвера, живёт в профиле драйвера, переустановку
Windows переживает. После «Предпочтителен режим максимальной производительности»
карта сразу пошла на 1650 МГц и 243 Вт с маской `Pwr` (0x4).

Уроки:

- **Низкие TFLOPS без объяснения — не диагноз.** Замер обязан снимать частоту,
  мощность и причину ограничения во время нагрузки. Теперь это делает
  `NvidiaLiveProbe` (поле `clocks_event_reasons.active`) и блок «Поведение под
  нагрузкой» в `GpuDiagnosticTest`.
- **Счётчик «загрузка 100%» ничего не говорит о мощности.** Карта на 1200 МГц
  и 0,79 В была «загружена на 100%». Смотреть надо на долю от лимита мощности
  и долю от предельной частоты.
- **Маска `Idle` при полной загрузке — признак зажима драйвером**, а не
  простоя. `Pwr` под тяжёлой нагрузкой — норма.
- **Собственный стресс-тест на этом фоне выглядел сломанным** (81–110 Вт) —
  и полдня ушло на его «починку». Сначала проверять, что карта вообще может
  разогнаться, потом чинить шейдер.

Проверено GPU-Z (встроен в FurMark 2, `gpuz\gpuz.exe -minimized -log файл`,
нужны права администратора): напряжение ядра 0,793 В при 1200 МГц → 0,83–0,84 В
при 1650; PerfCap 16 (Idle) → 1 (Pwr). Напряжения 12 В на слоте/6-pin/8-pin под
250 Вт: 11,6 / 11,7 / 11,8 — блок питания в порядке.


## Стресс-тест видеокарты: что мешало греть (2026-09-14)

Цель — нагрузка, сравнимая с тяжёлой игрой, чтобы ловить перегрев памяти.
Итог: 188–192 Вт при 1920–1935 МГц (было 135 при 1650), горячая точка 74,
память 73. Это потолок вычислительного шейдера на этой карте: FurMark берёт
250 Вт растеризацией, текстурами и ROP, которых у compute нет. Мощность не
менялась при любом балансе счёта и памяти — упёрлись в буст по напряжению,
а не в лимит мощности.

Что по дороге не работало и почему:

- **Один ресурс на двух UAV-слотах.** Поточный вызов ставил греющий буфер на
  слот 0, пока тот ещё висел на слоте 1 после счётного. Direct3D 11 молча
  отвязывает конфликтующий слот — вызов уходит в пустоту без единой ошибки.
  Снимать оба слота перед установкой, всегда.
- **Копирование внутри одного буфера — 12 ГБ/с.** `Heat[dst] = Heat[src]` по
  одному UAV: чтение и запись одного ресурса сериализуются. Чтение без записи
  греет память ровно так же, и ему ничто не мешает.
- **Восемь чтений на поток с шагом 256 МБ — 95 ГБ/с.** Каждый warp трогал восемь
  далёких страниц, таблица страниц карты не успевала. Один элемент на поток
  строго подряд, объём — второй осью `Dispatch`: по первой оси Direct3D даёт
  не больше 65535 групп.
- **Калибровка по первому вызову.** Первый вызов включает компиляцию шейдера
  драйвером и первое касание буфера — в десятки раз дольше настоящего. Замер
  по нему «превышал цель» и обрывал калибровку на минимуме итераций. Три
  прогревочных вызова до замера.
- **Обращения к памяти изнутри счётного цикла** тормозили FMA, а трафика давали
  мало (контроллер на 16%). Память — отдельным вызовом, счёт — чистым.

Сюда же: `nvidia-smi` на драйвере 616.92 отдаёт в маске причин биты `0x400` и
`0x600`, которых в старом NVML нет. В NVML 13 добавлены две причины —
`Reliability` (предел по надёжности напряжения, VRel у GPU-Z) и `BoardLimit`
(предел платы); документация даёт имена без чисел, свободные биты после 0x100 —
эти два. Разбираем их одной маской 0x600 как «потолок буста — норма»: под
нашим стрессом карта на 1935 МГц сидела именно на ней, а не на лимите
мощности.
