# Десктопная утилита аудита сети с игровым оверлеем — анализ и архитектура

**Дата:** 2026-08-16
**Что анализировалось:** возможность и способ реализации автономного Windows-приложения
для аудита качества сети в реальном времени, с графиками и оверлеем поверх игр.
**Статус:** только анализ, код не писался.

## Вводные (зафиксированы владельцем)

- Отдельное приложение, **никак не связано с VPN-проектом** и нодами Remnawave.
- **Полностью локальное:** серверной части нет, ничего не разворачивается на хостах.
- Платформа: **Windows** (только).
- Оверлей поверх игр: **layered-окно + опциональный RTSS**, без инъекций в процессы.
- Стек: **C# / .NET 8**.
- Аудитория: **для себя / узкого круга** → админ-права допустимы, подпись кода и
  инсталлер не требуются.
- Метрики (все четыре в скоупе): ping до сервера игры, локализация проблемы по
  участкам, bufferbloat + нагрузка по процессам, качество Wi-Fi.

## Ключевые технические выводы

### 1. Оверлей: почему layered-окно, а не хук

| Способ | Работает поверх | Риск |
|---|---|---|
| Layered topmost-окно | borderless / windowed (~90% современных игр) | нулевой |
| RTSS shared memory | всё, включая exclusive fullscreen, D3D9–12/Vulkan/GL | нужен установленный RTSS |
| Свой DXGI/Present hook + ImGui | всё | **бан античитами** (EAC, BattlEye, Vanguard, FACEIT) |

Инъекция DLL в процесс игры технически даёт лучший результат, но античиты
трактуют её как чит. RTSS решает ту же задачу без риска, потому что он давно
в белых списках античитов, и мы не пишем хук сами — только кладём строку в его
shared memory.

Практика layered-окна (WPF):
- `WindowStyle=None`, `AllowsTransparency=true`, `Topmost=true`, `ShowInTaskbar=false`.
- P/Invoke `SetWindowLong(GWL_EXSTYLE, WS_EX_LAYERED | WS_EX_TRANSPARENT |
  WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE)`:
  - `WS_EX_TRANSPARENT` — клики проходят насквозь в игру;
  - `WS_EX_NOACTIVATE` — окно не ворует фокус у игры (критично);
  - `WS_EX_TOOLWINDOW` — не появляется в Alt-Tab.
- **Грабля:** игра в borderless периодически перехватывает Z-order. Лечится
  таймером, который раз в 1–2 с переустанавливает `SetWindowPos(HWND_TOPMOST)`.
- **Грабля:** `AllowsTransparency=true` в WPF исторически ронял аппаратное
  ускорение окна. На современных Windows приемлемо, но оверлей должен рисовать
  минимум (текст + короткий спарклайн), а не полноценные графики.

RTSS-интеграция: shared memory `RTSSSharedMemoryV2`, структуры
`RTSS_SHARED_MEMORY` / `OSDENTRY`; пишем свою строку в свободный OSD-слот.
Есть готовая C#-обёртка `RTSSSharedMemoryNET` (так же делают HWiNFO и CapFrameX).
Оверхед околонулевой.

### 2. ICMP в Windows не требует прав администратора

`System.Net.NetworkInformation.Ping` — обёртка над `IcmpSendEcho2` (IP Helper API),
а не над raw-сокетами. Работает от обычного пользователя. Через `PingOptions.Ttl`
делается и traceroute/MTR — тоже без админа и без raw-сокетов. Это снимает
основную боль подобных утилит.

Ограничение метода: ICMP на транзитных роутерах обрабатывается по остаточному
принципу и его цифры не равны реальному игровому RTT. Поэтому ICMP-пробы надо
дублировать TCP-connect-пробой (время SYN→SYN/ACK) до порта, который у цели
реально открыт.

### 3. Автоопределение сервера игры — здесь нужен админ

Идея фичи: не пинговать 8.8.8.8, а найти IP, с которым процесс игры прямо сейчас
обменивается UDP, и строить графики именно до него.

- `GetExtendedTcpTable` даёт remote-адрес TCP-соединений по PID **без админа** —
  но игровой трафик почти всегда UDP, а TCP идёт только к мастер-серверу/логину.
- `GetExtendedUdpTable` (в том числе `UDP_TABLE_OWNER_MODULE`) отдаёт только
  **локальные** сокеты, remote-адреса там нет. Для UDP этот путь тупиковый.
- Рабочий способ — **ETW, провайдер `Microsoft-Windows-Kernel-Network`**: события
  `UdpIpSend`/`UdpIpRecv` содержат PID и daddr. Библиотека
  `Microsoft.Diagnostics.Tracing.TraceEvent`. **Требует прав администратора.**
- Тот же ETW-поток бесплатно закрывает вторую задачу — **трафик по процессам**
  (кто жрёт канал: торрент, Steam, обновления Windows).

Так как аудитория «для себя», админ-права приемлемы, и обе фичи делаются одним
механизмом. Для варианта без админа остаётся деградация: ручной ввод IP + подсказка
из TCP-таблицы.

### 4. Локализация проблемы по участкам

Самая полезная часть аудита — параллельные пробы на разной глубине, отрисованные
на одном таймлайне:

1. **ПК → роутер** (default gateway из `NetworkInterface`/`GetIPForwardTable`).
   Скачет только этот участок → виноват Wi-Fi/кабель/роутер.
2. **ПК → первый хоп провайдера** (hop 2 из traceroute, кэшируется).
   Скачет тут → last mile провайдера.
3. **ПК → якорь в интернете** (1.1.1.1 / 8.8.8.8).
4. **ПК → сервер игры** (см. п.3).

Вклад каждого сегмента = разница соседних уровней. На графике это stacked-области —
сразу видно, чей это миллисекунды.

### 5. Bufferbloat

Ключевая метрика для игр и та, которую обычные спидтесты прячут: рост RTT под
нагрузкой. Схема — замер baseline RTT в простое, затем нагрузка канала
(скачивание/отдача с публичной точки, например `speed.cloudflare.com` — своего
сервера не требуется) с одновременным замером RTT. Дельта → оценка по шкале
A–F в стиле Waveform Bufferbloat Test. Отдельно вниз и вверх: у домашних каналов
проблема обычно на upload.

### 6. Wi-Fi

`wlanapi.dll` через P/Invoke: `WlanOpenHandle` → `WlanQueryInterface`
(`wlan_intf_opcode_current_connection`) даёт RSSI, link quality, rx/tx rate, BSSID;
`WlanGetNetworkBssList` — соседние сети и загруженность каналов.

**Грабля:** начиная с Windows 11 24H2 доступ к SSID/BSSID требует включённых
служб геолокации и разрешения для приложения — иначе поля приходят пустыми.
Само качество связи (RSSI, link speed) при этом читается. Учитывать при UX.

### 7. Пропускная способность локально

`NetworkInterface.GetIPv4Statistics()` → дельта `BytesReceived/BytesSent` по
времени. Без админа, без драйверов, точность достаточная для графика загрузки
канала.

## Предлагаемая архитектура

```
NetAudit.sln
├── NetAudit.Core          — измерения, без UI
│   ├── Probes/            — IcmpProbe, TcpConnectProbe, TracerouteProbe,
│   │                        GatewayProbe, DnsProbe, ThroughputProbe, WifiProbe
│   ├── Etw/               — KernelNetworkListener (UDP-цели + трафик по PID)
│   ├── Analysis/          — сегментация задержки, jitter, loss, bufferbloat-скоринг
│   ├── Scheduler          — тики проб, PeriodicTimer + Stopwatch
│   └── Storage/           — SQLite (Microsoft.Data.Sqlite), история сессий
├── NetAudit.App           — WPF: главное окно, графики (ScottPlot 5)
├── NetAudit.Overlay       — layered click-through окно + хоткей
└── NetAudit.Rtss          — опциональный вывод в RTSS OSD
```

**Библиотека графиков:** ScottPlot 5 (WPF-контрол). Выбран за realtime: держит
десятки тысяч точек с перерисовкой без просадок, есть готовые стратегии
скользящего окна. LiveCharts2 красивее анимациями, но тяжелее на потоковых данных.

**Буферизация:** кольцевой буфер в памяти на графики (10 мин × 4 Гц ≈ 2400 точек
на серию), полная история — в SQLite, чтобы можно было вернуться к «вчера в 21:00
лагало».

**Тайминги:** `System.Timers.Timer` неточен; тик через `PeriodicTimer` +
`Stopwatch` для реальных интервалов. Штатное разрешение таймера Windows 15.6 мс,
для тика 250 мс достаточно, `timeBeginPeriod` дёргать не нужно.

## Этапы (по нарастанию риска)

| Этап | Содержание | Что проверяет |
|---|---|---|
| 0 | WPF + ScottPlot, ICMP-пробы до шлюза/DNS/произвольной цели, живой график | жизнеспособность ядра и графиков |
| 1 | Сегментация: шлюз → первый хоп → интернет, traceroute на TTL, «кто виноват» | главная аналитическая ценность |
| 2 | Layered-оверлей, click-through, хоткей, настраиваемый набор полей | главный технический риск |
| 3 | ETW: авто-детект сервера игры + пинг до него | самая ценная и самая хрупкая фича |
| 4 | Bufferbloat-тест + трафик по процессам (тот же ETW) | |
| 5 | Wi-Fi модуль | |
| 6 | RTSS-бэкенд для exclusive fullscreen, SQLite-история и просмотр прошлых сессий | |

Этап 2 стоит делать раньше этапа 3: оверлей — то, ради чего всё затевается, и его
поведение поверх конкретных игр надо проверить эмпирически как можно раньше.

## Организационное ограничение (важное)

Текущий хост — **Linux, .NET SDK не установлен** (`which dotnet` → пусто).

- Собирать WPF-проект на Linux технически можно: `dotnet publish -r win-x64` со
  свойством `EnableWindowsTargeting=true` в csproj.
- Но **запускать и отлаживать нельзя**: ни WPF-окно, ни ETW, ни WlanAPI, ни
  оверлей поверх игр на Linux не проверяются. Итерация «изменил → посмотрел»
  требует Windows-машины.

Практический вывод: разработку вести на Windows-ПК (это же и целевая машина —
там же и игры). Этот Linux-хост подходит только для хранения кода/репозитория.

## Границы анализа — что НЕ проверялось

- Не проверялась работа конкретных игр с античитами при layered-оверлее
  эмпирически (вывод о безопасности основан на принципе «нет инъекции в процесс»).
- Не проверялась актуальная структура RTSS shared memory для текущей версии RTSS.
- Не оценивалась точность ETW-событий `UdpIpSend/Recv` под высоким pps (возможна
  потеря событий при большом трафике; для определения IP цели это не критично,
  для точного подсчёта байт — надо мерить).
- Поведение Wi-Fi API на Windows 11 24H2+ описано по документации, на машине
  владельца не проверялось.
- Не рассматривались IPv6-сценарии отдельно (ETW и ICMP их поддерживают, но
  сегментация путей для IPv6 может отличаться).
